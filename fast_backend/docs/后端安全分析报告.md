# 后端安全分析报告（fast_backend）

> 生成方式：动态工作流（6 个安全域并行评审 → 每条发现由独立盲复核员重读代码确认 → 去重排序）
> 日期：2026-09-22
> 原始发现 28 条，去重后 **18 项**；其中 3 组同根因被多个域重复命中（6 位 PIN 爆破、`root:123456` 默认连接串、`echo=True` 日志泄露）。

---

## 一、结论

最该先堵的三件事：

1. **账户可被在线爆破接管**：全站口令被强制成「恰好 6 位数字」（空间仅 10⁶），登录限流按 `IP|用户名` 计数且为单进程内存，换代理 IP 池即可绕过 15 分钟锁定。
2. **AI/LLM 端点零配额、零并发、零限流**：任意（免费）注册用户可对第三方 LLM/Embedding 无界调用，直接烧操作者的账单与存储。
3. **JWT 无撤销机制**：改密不使旧令牌失效，泄露 token 在 24h 内持续可用；且 `JWT_SECRET_INSECURE_OK` 逃生门因变量绑定 bug 实际以**空密钥**签发。

优先级修复顺序：① PIN 口令策略 + 跨 IP 限流 → ② AI 配额 + 并发上限 → ③ JWT 撤销机制 → ④ 移除 `root:123456` 默认串 → ⑤ 关闭 `echo=True` → ⑥ 修 `JWT_SECRET_INSECURE_OK` 绑定。

---

## 二、高危（必须优先修）

### H1 · 6 位数字口令 + 按 IP 限流可绕过 → 在线爆破账户接管 【已复核】
- 位置：`schemas/users.py:13`（`PASSWORD_PATTERN = r"^\d{6}$"`，注册/改密同口径 :19/:61）、`routers/user.py:47`（限流键 `{client_ip}|{username}`）
- 证据：口令空间仅 10⁶；限流器 `utils/throttle.py` 为单进程内存字典，按 key 计 5 次/5min 锁 15min，无「单用户名跨 IP 总量」上限。复现：固定目标用户名，轮换 ~3000 个代理 IP，约 1 天可穷尽全空间，接管后读该用户全部财务数据。
- 修复：放宽口令策略（长度/复杂度/去纯数字）；限流改为「按用户名（不区分 IP）」或全局兜底计数；加验证码/指数退避。
- 状态：verified

### H2 · AI/LLM 端点无按用户配额 / 无并发 / 无限流 → 费用与存储滥用 【已复核】
- 位置：`routers/ai.py:166`（`/chat`、`/chat/stream`）、`:254-288`（`/analyze/*`）、`:404` 起（`/bookkeeping`）、`:311`（`/faq/search` → `ai/faq_retriever.py:73`）
- 证据：每个请求都产生真实第三方 LLM/Embedding 成本；全库 grep 确认 `utils/throttle.py` 仅用于登录，AI 侧零导入；`ai/llm.py` 的 `ChatOpenAI` 未设 `max_tokens`，输出无界且全量落库。配合无限流注册（`user.py:29`）可低成本放大。
- 修复：为全部 LLM 端点加每用户配额 + 并发上限；给 LLM 输出设 max_tokens；注册加限流。
- 状态：verified

## 三、中危

### M1 · JWT 无撤销 / 吊销机制 【已复核】
- 位置：`routers/user.py:110`（改密走 `crud/user.py:93` 只换哈希不动令牌）、`crud/user.py:77`（自述「无状态 JWT，user_token 吊销位未启用」）、`config/settings.py:37`（默认 24h）
- 修复：启用 `user_token` 表做吊销，或引入短有效期 + 刷新令牌；改密/登出时失效旧令牌。
- 状态：verified

### M2 · `JWT_SECRET_INSECURE_OK` 逃生门失效（变量绑定 bug）【已复核】
- 位置：`config/settings.py:36`（import 时绑定模块级 `JWT_SECRET`）与 `:77-78`（`os.environ.setdefault` 只改 `os.environ`，不回写已绑定常量）
- 证据：该路径下 `security.py` 实际以空字符串为密钥签 HS256，读源码者可离线伪造 admin token；误在生产开启即鉴权全绕过。（此点未实际运行复现，基于名称绑定语义判读）
- 修复：逃生分支应直接改写模块级 `JWT_SECRET` 变量，或重启后重读；生产禁用该开关。
- 状态：verified

### M3 · 默认连接串硬编码 `root:123456` 弱口令 【已复核】
- 位置：`config/db_config.py:21`（`os.getenv("DATABASE_URL", "mysql+aiomysql://root:***@localhost:3306/...")`）
- 证据：`.env` 未设 `DATABASE_URL` 时即以弱 root 口令连库；`.env` 本身已 gitignore（仓库无泄露凭据），但源码默认值随仓库分发。
- 修复：去掉危险默认值，缺失即启动报错（对齐 `JWT_SECRET` 的做法）。
- 状态：verified

### M4 · `echo=True` 恒开 → 财务/PII 写入日志 【已复核】
- 位置：`config/db_config.py:27`（`create_async_engine(DATABASE_URL, echo=True, ...)` 无环境开关）
- 证据：SQLAlchemy echo 会把含金额、手机号等参数的完整 SQL 打进 stdout/日志归档，成为数据泄露面，且拖慢每请求性能。
- 修复：`echo=DEBUG_MODE` 或环境变量控制，生产默认关。
- 状态：verified

### M5 · AI 持久化提示词注入 【已复核】
- 位置：`routers/ai.py:182/231`（`messages = [SystemMessage(SYSTEM_PROMPT), *history, HumanMessage(body.message)]`，history 来自 `ai/memory.py` 直读库）
- 证据：用户文本与历史无隔离直送 LLM，输出落库后作下一轮提示词，注入载荷同会话跨请求持续生效。影响限于本人会话内助手行为，故 medium。
- 修复：对入库/回注的历史做内容隔离与标记；system prompt 明确拒绝对诱导性指令。
- 状态：verified

### M6 · bookkeeping 去重 TOCTOU 竞态 → 重复入账 【已复核】
- 位置：`routers/ai.py:452`（先 `find_recent_by_dedup` 预检后 `INSERT`，`crud/ai.py:366-384`）
- 证据：`dedup_hash` 仅普通索引，唯一键只有 `(user_id, client_msg_id)`；并发同文且不带相同 `client_msg_id` 的两请求都过预检，各写一遍 `records`。
- 修复：给 `(user_id, dedup_hash, 窗口)` 加唯一约束，以 DB 唯一键兜底而非应用层预检。
- 状态：verified

### M7 · AI 会话创建 / 列表无上限 → 灌库与拉全表 【未证实，需人工确认】
- 位置：`routers/ai.py:66`（`POST /sessions` 无条件 insert）、`:85`（`list_sessions` 的 `size` 无 `le` 上限）
- 证据：无每用户会话数检查；`size` 可传超大值经 JOIN 聚合大量行。结合无限流注册为低门槛资源滥用。
- 修复：限制每用户会话数；`size` 设 `le` 上限。
- 状态：unconfirmed（复核员未能在现有证据中完全坐实，需人工确认）
