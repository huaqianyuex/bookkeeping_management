## 1. 范围与实施原则

### 1.1 文件范围

本方案将 Python 文件分为四类：

1. **直接修改文件**：当前总体计划明确要求调整生产代码。
2. **条件性修改文件**：仅当采用推荐架构或验收发现关联问题时修改。
3. **建议新增文件**：当前不存在，用于隔离限流、AI 配额、业务服务、图片验证、迁移和测试。
4. **明确不修改文件**：当前安全结论依赖这些文件的行为，但不应为了“顺便重构”而改动。

### 1.2 核心实施原则

- 路由层只处理 HTTP 参数、依赖、状态码和响应映射。
- 限流、配额、并发租约不能只写在路由中。
- 外部 LLM 调用不能放在长数据库事务中。
- 不使用公开固定的 JWT 逃生密钥。
- 不使用普通 `AsyncSession` 跨多次 `commit` 持有 MySQL `GET_LOCK`。
- LLM 输出限制必须进入 provider 客户端和结构化 Schema，不能只在响应后检查。
- `Record.type` 必须从分类推导；分类类型创建后不可变。
- 所有测试使用 fake LLM、fake clock 和隔离数据库，不调用真实付费接口。

## A. 配置、启动与数据库

### 1. `config/settings.py`

**文件路径：** `fast_backend/config/settings.py`

**当前相关位置：**

- 配置读取：`15-61`
- `_validate_security()`：`65-89`
- 启动时安全校验：`92`

**需要修复的问题：**

- M2：`JWT_SECRET_INSECURE_OK` 只修改 `os.environ`，没有更新已绑定的 `JWT_SECRET`。
- 生产环境可能接受弱密钥，或在逃生开关下继续使用空/可预测密钥。
- M1 所需的 token 生命周期、密钥轮换、上传限制、AI 配额、清理任务参数没有集中配置。
- `MAX_HISTORY_TOKENS`、`KEEP_RECENT_MESSAGES` 已存在，但 AI 侧未使用。

**具体修复方式：**

1. 修改 `_validate_security()`，不再调用 `os.environ.setdefault()` 作为修复。
2. 在函数开头读取并规范化 `APP_ENV`；生产环境必须显式配置高熵 `JWT_SECRET`。
3. 生产环境满足以下任一条件时抛出 `RuntimeError`：
   - `JWT_SECRET` 缺失；
   - 长度不足；
   - 命中公开弱默认值；
   - `JWT_SECRET_INSECURE_OK` 为真。
4. 开发环境未提供密钥时，使用 `secrets.token_urlsafe(48)` 在进程启动时生成临时随机密钥并输出明确告警；不得使用固定字符串。
5. 增加以下集中配置并校验范围：
   - `JWT_PREVIOUS_SECRET`、`JWT_ISSUER`、`JWT_AUDIENCE`；
   - `BCRYPT_ROUNDS`；
   - `TRUSTED_PROXY_CIDRS`；
   - AI 日配额、分钟速率、每用户并发、全局并发、各用途 `max_tokens`；
   - 活跃会话数、消息页大小、FAQ rebuild 冷却；
   - 幂等 lease 秒数；
   - 图片最大宽、高、像素数；
   - scheduler 开关、清理间隔、保留天数、批大小。

**原因和预期效果：**

- 消除空密钥和公开 fallback，生产配置错误在启动时暴露。
- 所有安全阈值可审计、可压测、可回滚，不再散落为魔法数字。
- 为 Redis 限流、AI Guard、上传验证和清理任务提供单一配置源。

**依赖与验收：**

- 依赖部署环境确认生产 profile。
- 测试缺失/弱 JWT、生产逃生开关、非法数值配置和开发随机密钥。

### 2. `config/db_config.py`

**文件路径：** `fast_backend/config/db_config.py`

**当前相关位置：**

- `DATABASE_URL` 读取：`19-22`
- `create_async_engine()`：`25-30`
- `AsyncSessionLocal`：`33-37`
- `get_db()`：`41-48`

**需要修复的问题：**

- M3：缺少 `DATABASE_URL` 时回退到源码中的弱连接串。
- M4：`echo=True` 硬编码，SQL 参数可能进入日志。
- 当前 SQLite 测试会因 MySQL 专用 `pool_size`、`max_overflow` 参数失败。
- CRUD 内部多次 `commit` 会让幂等事务和 SSE 生命周期难以控制。

**具体修复方式：**

1. 移除弱默认连接串；`DATABASE_URL` 缺失时启动失败。
2. 从 `settings.py` 读取 `APP_ENV`、`DEBUG_MODE` 和显式 SQL 日志开关。
3. 创建引擎时改为：
   - 生产 `echo=False`；
   - `hide_parameters=True`，除非显式开发调试；
   - 仅对 MySQL/PostgreSQL 等需要连接池的方言传 `pool_size`、`max_overflow`。
4. 保留 `expire_on_commit=False`；当前没有证据需要改变。
5. `get_db()` 的异常回滚逻辑保留；不要在本次安全整改中大规模重写。
6. 为 AI 流式生成、幂等服务和清理任务提供“自行创建并关闭短生命周期 session”的工厂，而不是复用请求级 generator。

**原因和预期效果：**

- 生产不会静默使用弱数据库凭据。
- SQL 参数、金额、手机号和聊天数据不再默认进入日志。
- 测试可使用 SQLite 单元测试，MySQL 行为由专用集成测试覆盖。

**依赖与验收：**

- 不打印完整连接串。
- 测试缺配置启动失败、`DEBUG=false` 时 `echo=False`、异常后 session 回滚关闭。

### 3. `main.py`

**文件路径：** `fast_backend/main.py`

**当前相关位置：**

- `app = FastAPI()`：`18`
- 上传目录和静态挂载：`32-34`
- `health()`：`37-40`
- 路由注册：`43-49`

**需要修复的问题：**

- 当前没有 lifespan，无法启动/停止清理任务。
- `/api/health` 只返回静态状态，不检查数据库 readiness。
- 上传目录在模块导入时创建，静态文件响应没有 `nosniff`。
- FAQ 索引没有明确启动状态；多 worker 各自持有不同内存状态。
- 缺少对“生产必须单 worker 或已配置 Redis”的启动约束。

**具体修复方式：**

1. 新增 `lifespan()`：
   - 启动时创建必要目录；
   - 根据 `ENABLE_SCHEDULER` 启动清理任务；
   - 根据配置决定是否预热 FAQ；
   - 关闭时停止 scheduler、释放 AI/Redis 资源。
2. 改为 `app = FastAPI(lifespan=lifespan)`。
3. 保留 `/api/health` 作为 liveness；新增 `/api/ready` 执行 `SELECT 1` 并检查必要依赖。
4. 为 `/uploads` 响应增加 `X-Content-Type-Options: nosniff`。
5. 不在每次 worker 启动时无条件调用付费 FAQ rebuild；预热必须有开关、冷却和降级状态。
6. 如果 P0 仍使用内存限流，生产配置检测到多 worker 时启动失败或明确告警；生产 Redis 方案完成后解除。

**原因和预期效果：**

- 应用启动、关闭和后台任务生命周期可测试。
- 负载均衡器能区分“进程活着”和“依赖已就绪”。
- 避免导入测试时意外创建目录、调用外部服务或启动后台线程。

**依赖与验收：**

- 测试 lifespan、readiness、scheduler 只启动一次、静态响应头和无付费 FAQ 预热。

## B. 用户、密码、JWT 与限流

### 4. `schemas/users.py`

**文件路径：** `fast_backend/schemas/users.py`

**当前相关位置：**

- `PASSWORD_PATTERN`：`11-13`
- `RegisterRequest`：`16-34`
- `LoginRequest`：`37-40`
- `UserUpdateRequest`：`43-55`
- `PasswordChangeRequest`：`58-70`
- `UserOut`：`73-83`

**需要修复的问题：**

- H1：新注册和改密只允许 6 位纯数字。
- 注册、登录、资料修改对用户名规范化不一致，可产生不同限流键。
- `LoginRequest.username` 没有长度上限。
- 若存量 6 位 PIN 用户要强制迁移，当前响应模型没有“需要改密”状态或新 token 返回契约。

**具体修复方式：**

1. 新增唯一的 `canonical_username(value)`，至少执行 `strip()`；大小写折叠规则必须与 MySQL collation 一致。
2. `RegisterRequest`、`LoginRequest`、`UserUpdateRequest` 全部复用该函数。
3. 将 6 位正则替换为集中式 `validate_password_policy()`：
   - 新密码建议 12–128 位；高敏公网场景采用 15–128；
   - 拒绝纯数字短 PIN、常见密码和空白；
   - 不强制无意义的固定符号组合。
4. `LoginRequest.password` 不执行新密码强度校验，只做必要长度上限，否则存量用户无法登录。
5. `UserUpdateRequest` 不允许修改用户名；用户名唯一性只在注册阶段确定。
6. 如果采用“存量用户下次登录强制改密”，增加 `password_migration_required` 输出字段，并定义改密后返回新 access token 的响应模型。

**原因和预期效果：**

- 扩大密码空间，阻止 10^6 PIN 暴力枚举。
- 注册、登录、限流使用同一账号标识，消除大小写/空格变体绕过。
- 登录接口仍能兼容旧密码，迁移过程可控。

**依赖与验收：**

- 依赖 Web、uniapp 同步修改密码规则。
- 测试旧 PIN 登录兼容、新注册拒绝 PIN、用户名变体归一、响应契约。

### 5. `routers/user.py`

**文件路径：** `fast_backend/routers/user.py`

**当前相关位置：**

- `register()`：`30-39`
- `login()`：`43-77`
- `get_user_info()`：`81-90`
- `update_user()`：`99-106`
- `change_password()`：`110-117`
- `upload_avatar()`：`121-144`

**需要修复的问题：**

- H1：登录只按 `IP|username` 限流，可被换 IP 绕过。
- L2：注册明确返回“用户名已存在”，登录未知用户跳过 bcrypt，存在响应和时序枚举。
- L3：注册无限流，存在 check-then-create 竞态。
- M1：改密后旧 token 继续有效。
- L1：密码验证成功后没有渐进式 rehash。

**具体修复方式：**

1. `register()`：
   - 请求进入后先执行注册 IP/全局限流；
   - 移除路由层“先查用户名”作为最终裁决；
   - 直接调用 CRUD，捕获唯一键冲突；
   - 对成功、重复、竞态冲突使用统一外部文案，避免用户名 oracle。
2. `login()`：
   - 使用 `canonical_username()` 和 `get_trusted_client_ip()`；
   - 调用 `LoginGuard.check()`，命中时返回 429 和 `Retry-After`；
   - 用户不存在时执行 `verify_dummy_password()`；
   - 密码正确后检查账号状态；
   - 密码验证成功后检查 `password_needs_rehash()`，升级旧 bcrypt 哈希；
   - 成功后仅清理对应风险桶，不无条件清除所有全局失败记录。
3. `change_password()`：
   - 调用 `crud.user.update_password()`，在同一事务更新密码哈希和 `token_version`；
   - 改密成功后签发新 token 返回，避免用户立即掉线；
   - 旧 token 在响应发出后立即 401。
4. `upload_avatar()` 路径保持调用 `save_avatar()`，但后者改为完整解码和重编码。

**原因和预期效果：**

- 跨 IP 针对同一账号仍受限，单 IP 喷洒账号也受限。
- 用户名存在性不再直接暴露，bcrypt 计算量更稳定。
- 注册竞态由数据库唯一键裁决，改密能撤销泄露 token。

**依赖与验收：**

- 依赖 `LoginGuard`、可信 IP 解析、`token_version` 和 dummy hash。
- 测试第 6 次失败 429、伪造 XFF、同账号多 IP、同 IP 多账号、并发同名注册、改密旧 token 401。

### 6. `crud/user.py`

**文件路径：** `fast_backend/crud/user.py`

**当前相关位置：**

- `get_user_by_id()`：`12-15`
- `get_user_by_username()`：`18-21`
- `create_user()`：`24-44`
- `create_token()`：`77-88`
- `update_password()`：`93-109`

**需要修复的问题：**

- L3：注册逻辑先查后插，无法消除并发竞态。
- M1：`create_token()` 不携带撤销版本。
- `update_password()` 只更新哈希，不更新 token 生命周期。
- `create_token()` 的注释称不查库，但当前鉴权实际上会查用户状态，注释已过时。

**具体修复方式：**

1. `get_user_by_username()` 接收已规范化用户名，不添加 `FOR UPDATE`。
2. `create_user()` 只负责构造和持久化；唯一键异常交给路由/全局异常层处理。
3. `create_token()` 改为接收 `AsyncSession`、用户 ID 和 `token_version`，或直接接收 `User`。
4. `update_password()` 使用单条 SQL 原子更新：
   - 新密码哈希；
   - `token_version = User.token_version + 1`。
5. 新增 `replace_password_hash()`，仅用于登录成功后的透明 rehash，不改变用户密码语义。
6. 如果实现 `must_change_password`，创建新用户默认 `False`，存量迁移设为 `True`。

**原因和预期效果：**

- 数据库唯一键成为并发注册最终裁决者。
- 密码和撤销版本同事务提交，避免出现“密码已改但旧 token 仍有效”的中间状态。
- 旧低成本 bcrypt 可渐进升级，不要求全员集中改密。

**依赖与验收：**

- 依赖 `models/user.py`、JWT claim、数据库迁移。
- 测试并发注册、版本原子递增、改密事务回滚和 rehash。

### 7. `utils/security.py`

**文件路径：** `fast_backend/utils/security.py`

**当前相关位置：**

- `hash_password()`：`17-20`
- `verify_password()`：`23-28`
- `create_access_token()`：`31-37`
- `decode_access_token()`：`40-42`

**需要修复的问题：**

- L1：bcrypt 固定 `rounds=10`，没有渐进升级。
- M1：JWT 只有 `sub`、`exp`，无 token 版本、签发时间、issuer、audience、类型。
- JWT 解码没有强制 `exp`、`sub` 必填。
- M2：密钥轮换没有当前/上一把 key 的受控验证机制。

**具体修复方式：**

1. `hash_password()` 从 settings 读取 `BCRYPT_ROUNDS`，压测后默认 12；继续兼容旧 `$2a$/$2b$/$2y$`。
2. 新增：
   - `password_needs_rehash(hashed)`；
   - `verify_dummy_password(plain)`；
   - 严格 Bearer/claim 辅助函数可放在新 `auth_policy.py`。
3. `create_access_token()` 增加：
   - `iat`；
   - `tv`；
   - `typ="access"`；
   - 可选 `iss`、`aud`、`jti`。
4. `decode_access_token()` 固定 `algorithms=["HS256"]`，设置 `require=["sub", "exp"]`。
5. 密钥轮换时先尝试当前 key，再在非生产过渡期尝试 previous key；如果旧 key 曾经泄露，不允许宽限。

**原因和预期效果：**

- 新密码使用更高成本，旧密码在成功登录时自动升级。
- 改密后可通过 `tv` 立即撤销旧 token。
- 缺少过期或 subject 的签名 token 不再被接受。

**依赖与验收：**

- 不得记录 secret、完整 token 或完整 payload。
- 测试旧 hash、rehash、缺 claim、错误算法、错误 key、版本不匹配和轮换。

### 8. `utils/auth.py`

**文件路径：** `fast_backend/utils/auth.py`

**当前相关位置：**

- `get_current_user()`：`17-37`
- `get_optional_current_user()`：`40-58`
- `get_current_admin()`：`61-77`

**需要修复的问题：**

- `authorization.replace("Bearer ", "")` 不是严格 Bearer 校验，纯 token 也可能通过。
- `int(user_id)` 位于异常范围外，非法 `sub` 可能返回 500。
- 缺失 header 依赖全局校验处理，可能返回 422 而不是 401。
- 没有校验 `token_version`。
- 认证、optional auth、admin auth 存在重复逻辑。

**具体修复方式：**

1. 抽取内部 `_resolve_token()`，统一完成：
   - scheme 校验；
   - JWT 解码；
   - subject 正整数校验；
   - 用户存在和启用状态校验；
   - `tv` 与数据库 `User.token_version` 比较。
2. `get_current_user()` 调用该函数并保持返回 `int`，避免修改所有业务路由。
3. 所有无效认证统一抛 401；管理员角色不足统一 403。
4. `get_optional_current_user()` 复用相同解析，但把无效 token 转为 `None`，不产生 500。
5. `get_current_admin()` 继续从数据库读取 role，不信任 JWT 中自包含角色。

**原因和预期效果：**

- 认证失败不再出现 422/500 分裂。
- 改密、禁用、角色变更后的旧 token 无法继续访问。
- 保留当前鉴权回查用户状态的现有安全能力。

**依赖与验收：**

- 测试无 header、错误 scheme、纯 token、非法 `sub`、过期、版本不匹配、用户禁用/删除、管理员降权。

### 9. `utils/throttle.py`

**文件路径：** `fast_backend/utils/throttle.py`

**当前相关位置：**

- `_Bucket`：`27-30`
- `LoginThrottle`：`33-50`
- `is_locked()`：`61-73`
- `record_fail()`：`75-86`
- `reset()`：`88-92`
- 全局实例：`95`

**需要修复的问题：**

- H1/L9：只有单一 `IP|username` 桶，没有账号维度和纯 IP 维度。
- `is_locked()` 与 `record_fail()` 不是一个原子操作，多个并发请求可同时进入 bcrypt。
- 进程内字典不跨 worker。
- 固定窗口注释与实际行为不完全一致；高基数键可增长。

**具体修复方式：**

1. 将当前实现降级为 `MemoryLoginGuard`，明确只支持单进程。
2. 抽象 `LoginGuard` 接口：`reserve/check`、`record_failure`、`reset`、`retry_after`。
3. 分离：
   - `account:{canonical_username}`；
   - `ip:{trusted_ip}`；
   - 可选全局桶。
4. 在执行 bcrypt 前原子预留失败名额，避免并发穿透。
5. 内存版使用 `time.monotonic()`、键长度限制和最大键数。
6. 生产多 worker 使用新 `utils/redis_guard.py`，通过 Redis Lua 原子完成检查、递增和 TTL。
7. Redis 故障策略必须显式配置；推荐敏感端点 fail-closed，不静默退回无限流。

**原因和预期效果：**
