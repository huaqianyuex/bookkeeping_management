# 兑换码运营方案 — 生成 / 分发 / 防刷 / 渠道追踪 / 活动与风控

> **定位**：会员兑换码（`membership_codes`）投入真实运营（社群 / 短信 / 邮件 / 合作方 / 线下物料）前的完整作战方案。
> **关联文档**：会员功能设计见 `docs/membership-plan.md`（表结构 / 叠加语义 / 核销行锁）；充值购买见 `docs/fastapi-backend/11-充值与审批模块.md`。
> **现状基线**：扩展版后端 `fast_backend -fwature-expansion-version`，分支 `refactor/frontend-directory-by-domain`。
> **阅读须知**：方案中每一项都标注了【已就绪】或【需开发】；P0 项未落地前不应进行大规模投放（见 §8）。

## 1. 生成与数量控制

**批次是运营的最小单元**：一次活动 × 一个渠道 = 一个批次。命名规范：

```
ACT{日期}-{渠道缩写}-{序号}     例：ACT20261011-QQUN-01（QQ 群）、ACT20261012-SMS-01（短信）
```

现有 `batch_no` 字段直接承载；管理端生成时显式传入，不留空（缺省时间戳无法归因）。

### 1.1 三层数量控制

| 层 | 控制手段 | 依赖 |
|----|----------|------|
| 生成侧 | 批次计划量 = 渠道触达预估 × 领取率（经验 5%~20%），宁少再补；单次 ≤500 张走现有接口，大批次分多次生成 | ✅ 已就绪 |
| 发放侧 | 渠道按「发放包」出库并登记（发放时间 / 数量 / 负责人 / 交付方式），未发放的码不出库 | 纯运营纪律 |
| 核销侧 | 批次总量上限 + 全局每日核销上限，超限熔断该批次（见 §6） | ❌ 需开发 |

### 1.2 生成纪律

- **按需分批，不预生成大量闲置码**——每一张未核销的码都是风险敞口（可被泄露、枚举试错）；
- 码值保持 16 位，**不要为线下物料缩短**：16 位无歧义字母表（31^16 ≈ 10^23）不可枚举，短码反而打开撞库空间；
- 每批生成后立即登记元数据（渠道 / 数量 / 天数 / 有效期 / 负责人），形成批次台账；
- 线下物料印刷前先抽 2~3 张走完整核销流程验证。

## 2. 渠道分发

### 2.1 渠道形态与适配

| 渠道 | 分发形态 | 防护要点 |
|------|----------|----------|
| 社群（QQ / 微信群） | 明码 + 活动说明，限量先到先得 | 限量批次控制总量；发码时部分字符打码引导进群领取；活动说明写清核销入口与有效期 |
| 短信 | 精准触达，天然 1 人 1 码 | 码与手机号绑定，仅该账号可核销（❌ 需开发，P2） |
| 邮件 | 同短信 | 同上 |
| 合作方 | 专属批次 + 专属导出文件 | 批次隔离；约定上限与核销数据对账口径；交付文件加密 |
| 线下物料（海报 / 卡片） | 印刷码 | 高价值场景加刮开验证位；导出文件加密；物料回收销毁未发放码 |

### 2.2 归因口径（关键决策）

**渠道归属写在码上，不依赖用户自填**：

- 码在生成时即随批次携带渠道属性（❌ 需开发 `channel` 字段），核销数据天然按渠道聚合；
- 不采用「用户核销时选择/填写来源」作为主归因——可造假、有人不填、事后无法校验；
- 用户自填来源至多作为校验性参考字段，不进报表主口径。

## 3. 防羊毛党（分层）

### 3.1 事前（设计态）

| 措施 | 状态 |
|------|------|
| 码值不可枚举（16 位无歧义字母表） | ✅ |
| 1 码 1 账号（核销行锁 + `used_by`） | ✅ |
| 短信/邮件渠道 1 人 1 码 | ✅（渠道形态天然满足）|
| 码与手机号/邮箱绑定 | ❌ P2 可选 |
| 核销要求账号注册满 N 天 | ❌ P2 可选 |

### 3.2 事中（运行态，按性价比排序）

| # | 措施 | 说明 | 状态 |
|---|------|------|------|
| 1 | **每账号每批次限核 1 张** | 防「堆码叠时长」——叠加语义下羊毛党核心收益就是把同批次多张码堆到一个账号；核销时校验该用户在本批次是否已有核销记录 | ❌ 需开发（P0）|
| 2 | **核销接口限流** | 复用 `utils/throttle.py::SlidingWindowRateLimiter`，单用户约 5 次/分钟；超限 429 | ❌ 需开发（P0，工作量极小）|
| 3 | 同 IP 高频核销告警 | 仅告警不拦截，阈值放宽防校园/公司 NAT 误伤 | ❌ 需开发（P1）|
| 4 | 批次熔断 | 批次核销速率异常（如 10 分钟内核销 30%）自动/手动暂停该批次 | ❌ 需开发（P1）|

### 3.3 事后（排查与处置）

- **异常画像**（每日核销数据里看）：新注册账号密集核销、同 IP 多账号、集中时段爆发、单账号多批次叠码；
- **处置手段（已就绪）**：未核销码作废（现有接口）+ 违规账号禁用（禁用后登录即 401，会员权益随之不可用——过期惰性降级体系下无需回收天数）；
- 批量作废按批次一键执行：❌ 需开发（P1，现有为单码作废）。

## 4. 渠道核销数据追踪

### 4.1 数据基础

- 核销事实（`used_by` / `used_at`）已有；缺的是「码 → 渠道」的归属维度：
  - ❌ `membership_codes` 增加 `channel` 字段（生成时随批次写入），或独立渠道/活动表；
- 统计为纯聚合查询，不涉及新事实数据采集。

### 4.2 统计接口（❌ 需开发）

`GET /api/admin/membership/codes/stats?batch=&channel=`（`get_current_admin`），按批次/渠道聚合：

| 指标 | 口径 |
|------|------|
| 发放量 | 批次内码数（status != 已作废）|
| 核销量 | `status = 1` 计数 |
| 核销率 | 核销量 / 发放量 |
| 新用户占比 | 核销用户中「核销时间距注册 ≤ N 天」的比例 |
| 平均核销时长 | `used_at - 批次发放时间` 中位数 |

### 4.3 报表节奏

- 活动期间每日拉一次（管理端报表页或导出）；
- 结项出报告：`到达 → 领取 → 核销` 漏斗 + 渠道 ROI 排序，决定下期预算分配；
- React 管理端「会员管理」页加统计面板（❌ 需开发）。

## 5. 活动流程（SOP）

1. **立项**：定目标（拉新 / 促活）、预算天数、渠道组合、各渠道码量与排期；
2. **生成与登记**：管理端按批次生成（显式 `batch_no`），登记渠道 / 数量 / 天数 / 有效期 / 负责人；
3. **投放前抽验**：每批抽 2~3 张走完整核销流程（生成 → 核销 → 权益生效 → 用量口径正确）；
4. **投放与监控**：按渠道排期发放；每日看 §4 统计 + §3.3 异常画像；
5. **收尾**：活动结束或量尽后，未核销码**整批作废**；出结项报告；
6. **复盘**：渠道 ROI 排序 → 下期渠道组合与码量调整。

## 6. 风控预案（分级响应）

| 级别 | 触发征兆 | 响应动作 |
|------|----------|----------|
| **L1 观察** | 核销速率上升、新号占比升高、单批次核销加速 | 提高查看频率至每 2~4 小时；收紧核销限流阈值 |
| **L2 处置** | 确认脚本攻击 / 批量异常核销 | 熔断批次（暂停核销，❌ 需开发）→ 排查 → 未核销码作废 → 违规账号禁用 |
| **L3 泄露** | 码表外流（交付文件泄露 / 合作方侧泄露） | 整批作废 + 换新批次重发；社群统一口径公告（活动提前结束 / 补发说明） |

**预案演练**：大规模投放前，把三条处置路径实际操作一遍并确认生效——

- [ ] 作废：作废一张码后核销返回「兑换码已作废」；
- [ ] 熔断：暂停批次后核销返回对应提示（P1 落地后）；
- [ ] 禁用账号：禁用后该账号登录即 401、前端跳登录页。

**沟通口径**：社群公告统一模板（提前结束原因 / 补发安排 / 新活动时间），避免逐条回复引发二次传播。
