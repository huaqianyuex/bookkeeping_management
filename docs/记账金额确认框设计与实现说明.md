# 记账「金额确认框」设计与实现说明

> 适用端：uni-app 移动端（语音记账 / 文字记账均在此端）
> 关联代码：`personal-ledger-uniapp/src/components/AmountConfirmPanel.vue`、`src/pages/ai-chat/index.vue`、`src/api/ai.js`
> 关联后端契约：`POST /api/ai/bookkeeping`（`fast_backend -fwature-expansion-version/routers/ai.py`）
> 关联测试：`fast_backend -fwature-expansion-version/tests/test_bookkeeping_preview_confirm.py`

---

## 1. 需求与范围

| 需求 | 落地方式 |
|---|---|
| 语音/文字输入完成后**自动**触发确认框 | 语义记账改为「**先预览、后入账**」两步：预览命中消费即弹框 |
| 确认框内**展示**本次输入的金额 | 渲染 `preview.items[]` 的 `amount` / `amountRaw` / 分类 / 日期 |
| 金额**允许手动修改** | 每条金额为可编辑输入框（`type="digit"`），点击即改 |
| 基于**修改后**的金额确认 | 确认时回传 `overrides=[{index, amount}]`，服务端按 index 覆盖后入账 |

**范围界定**：本次只改移动端（uni-app）。Web 端 `personal-ledger-frontend/src/pages/AiChat.jsx` 是纯问答助手，**没有**记账能力，故不涉及。后端契约此前已实现（`dryRun` / `overrides` / `preview`），本次**不改后端**，只补前端。

## 2. 触发时机

**触发点唯一**：`handleSend()` 中语义记账预览返回 `action === 'preview'` 时。

```
用户完成输入 ──► 发送 ──► 语义记账预览(dryRun=true)
                              │
        ┌─────────────────────┼──────────────────────────┐
        │                     │                          │
  action=preview        action=ignored             error / 网络异常
        │                     │                          │
   弹金额确认框          降级流式对话                 提示或降级对话
```

细分四种情况：

| 预览返回 | 是否弹框 | 说明 |
|---|---|---|
| `action = "preview"` 且 `items` 非空 | **弹** | 命中消费，进入确认流程 |
| `action = "ignored"`（`not_expense` / `query`） | 不弹 | 非消费类消息，回退到 AI 流式对话 |
| `{"error": ...}`（LLM 不可用等） | 不弹 | 降级流式对话，与改造前行为一致 |
| `{"error": ..., "code": "RATE_LIMIT"}` | 不弹 | 预览限流（20 次/分），提示后终止且**不落库** |

**语音与文字共用同一触发路径**：语音只是把识别文本回填输入框（`handleTranscribe`），用户点发送后走的是同一条 `handleSend`。二者差别仅体现在确认框上的来源标签（「语音识别」/「文字输入」）与随请求上报的 `source` 字段（仅审计用途）。

**「自动」的边界**：确认框在**预览返回后**自动弹出，不需要用户再点一次按钮；但**不**在录音结束/输入框有内容时就弹——因为此时尚未知道输入是否构成一笔消费，也没有可展示的金额。

## 3. 显示内容

确认框为**底部弹层**（`confirm-mask` + `confirm-sheet`），自上而下：

1. **标题行**：`确认记账金额` + 来源标签（语音识别 / 文字输入）
2. **副标题**：`请核对金额，可直接修改后再入账`
3. **条目列表**（`scroll-view`，最高 52vh）：每笔一行
   - 左：分类名（缺省显示「未识别分类」）、收支标签（支出/收入，`type` 为 null 时不显示）
   - 左下行：日期（`date` → `dateExpr` → 「今天」兜底）、`识别为「35块」` 原文片段、低置信度提示「把握不大」（`confidence ∈ (0, 0.5)`）
   - 右：**可编辑金额**，`¥` + 输入框，等宽数字排版（`--font-amount`）
4. **合计**（仅多笔时）：`共 N 笔 · 合计 ¥xx.xx`，随编辑实时重算
5. **服务端提示**：`preview.warnings[]`（如「未识别到明确分类，已归入「其他」」「识别把握不大，请核对金额与分类」）
6. **错误行**：金额非法时的说明文案
7. **操作区**：`取消` / `确认记账`

金额以 `amountRaw`（识别原文）与可编辑数值并列呈现，用户能对照「AI 听到的」与「AI 理解的」，这是本需求「展示金额」的关键信息量。

## 4. 编辑交互

| 交互 | 行为 |
|---|---|
| 点击金额 | 输入框聚焦，拉起数字键盘（`type="digit"`，含小数点） |
| 输入过滤 | `sanitizeAmount()`：只保留数字与一个小数点；整数位 ≤ 8 位、小数位 ≤ 2 位；多余小数点自动去除 |
| 校验规则 | 非空、`> 0`、`≤ 99,999,999.99`（与后端 `BookkeepingOverride.amount` 约束一致） |
| 非法反馈 | 行内输入框转红底红框 + 分类名转红 + 底部错误文案；`确认记账` 置灰 |
| 焦点提示 | 正在编辑的行分类名转琥珀色（`--color-accent-deep`） |
| 缺金额条目 | 输入框为空、placeholder `0.00`；**必须补全**才能确认（避免服务端把缺金额条目静默丢弃） |
| 多笔编辑 | 每笔独立编辑，合计实时联动 |

**只回传改动项**：`buildOverrides()` 仅收集「金额发生变化」或「原本缺金额被补上」的条目，减少无效覆盖与审计噪声：

```js
rows.filter(r => r.originalAmount === null || Number(r.amountText) !== r.originalAmount)
    .map(r => ({ index: r.index, amount: Number(r.amountText) }))
```

**`index` 是覆盖键，不是数组下标**：`index` 来自服务端 `parsed.items` 的下标，缺金额的条目同样占一个 index。用行号会导致「改第 3 笔写到第 2 笔」。

## 5. 确认流程

```
确认框「确认记账」
   │
   ├─ buildOverrides()  ──► overrides = [{index, amount}, ...]
   │
   └─ POST /api/ai/bookkeeping
        { message: 原文, clientMsgId: 预览时那个, previewId: 预览返回的 requestId,
          draftId, source, overrides }
        （dryRun 缺省 false → 真正入账）
   │
   ├─ action=created    → 渲染 echo（「已记下：餐饮 ¥50.00 · 2026-10-13 · 记录 #123」）
   ├─ action=duplicate  → 渲染 echo（连点确认被幂等拦下，未重复入账）
   ├─ action=clarify    → 兜底：仍缺金额，挂起 draftId 继续追问
   ├─ action=ignored    → 渲染服务端提示
   ├─ QUOTA_EXCEEDED    → 弹「额度已用完」弹窗
   └─ {"error"}         → 渲染失败文案
```

**四条硬约定**：

1. **同一 `clientMsgId` 贯穿预览与确认**：`clientMsgId` 在预览前生成，随预览结果挂起在 `pendingConfirm`，确认时复用。连点「确认记账」时，第二次请求会命中服务端幂等键返回 `duplicate`，**不会重复入账**。若两次用不同 key，连点就会入账两笔。
2. **回传 `previewId`（= 预览响应的 `requestId`）复用解析结果**：服务端把预览时的 `Parsed` 按 `requestId` 暂存在进程内 TTL 缓存里，确认命中时**跳过第二次 LLM 解析**，确认耗时由秒级降到毫秒级。未命中（重启 / 多 worker / TTL 过期 / 换用户 / 换消息 / 未回传）一律回退到重新解析——**只慢不错**，因此该字段是可选优化项，旧客户端不传也能正常工作。
3. **配额只在确认那次扣一次**：`dryRun=true` 不计 `daily_bookkeeping` 配额，改走独立预览限流；确认（`dryRun=false`）才扣 1 次。这样「预览 + 确认」整体只消耗 1 次额度，而不是 2 次。
4. **取消即丢弃**：点「取消」或点遮罩关闭 → 关闭弹层、清空 `pendingConfirm`，**不落库、不占配额**，并 toast「已取消，本次未记账」。用户消息气泡保留（那是用户真实输入）。

**防重复提交**：提交期间 `confirmSubmitting = true`，确认按钮进入 loading 且禁用，取消按钮同时禁用。

## 6. 与现有记账流程的衔接

### 改造前

```
输入 → 语义记账(dryRun=false) → created 直接入账
```

### 改造后

```
输入 → 语义记账预览(dryRun=true) → preview → 金额确认框 → 确认(dryRun=false + overrides) → created
```

衔接要点：

| 原有能力 | 衔接方式 |
|---|---|
| **追问续写**（`clarify` + `draftId`） | 保留。`draftId` 在预览与确认两次请求都带上；确认成功后服务端把草稿置为已消费。因为确认框强制补全金额，正常路径已不再走 `clarify`，仅作兜底 |
| **幂等去重**（`clientMsgId` / `dedup_hash`） | 预览不写日志、不占幂等键；真正落库只发生在确认那次，语义不变 |
| **配额闸门** | 确认那次才扣 `daily_bookkeeping`；预览走 `bookkeeping_preview_rate_limiter` |
| **非消费消息降级对话** | `ignored` 分支不变，仍回退 AI 流式对话 |
| **额度用尽弹窗** | `QUOTA_EXCEEDED` 处理不变（撤回用户气泡 + 弹窗） |
| **审计来源 `source`** | 预览与确认都带 `source`（voice/text），最终落在 `ai_bookkeeping_logs.source` |
| **新建对话** | `handleNewChat()` 额外关闭确认框并清空 `pendingConfirm`，避免预览串到新会话 |
| **对话历史** | 预览不写会话消息；确认时服务端写入 user + assistant 两条，与本地 `messages` 一致，不产生重复 |

### 函数职责重划

| 函数 | 改造前 | 改造后 |
|---|---|---|
| `tryBookkeeping` | 单次请求 + 分支渲染 | 拆分为 **`previewBookkeeping`**（只预览，返回动作指令） |
| `handleSend` | 直接渲染结果 | 按 `outcome.type` 分流：quota / error / reply / **confirm** / 降级对话 |
| `handleConfirm` | — | **新增**：带 overrides 入账并渲染结果 |
| `handleConfirmCancel` | — | **新增**：丢弃预览 |

## 7. 接口契约（本次依赖的字段）

**预览请求**

```json
{ "message": "午饭35块", "sessionId": "s-1", "clientMsgId": "uuid",
  "source": "voice", "dryRun": true }
```

**预览响应（`action=preview`）**

```json
{ "action": "preview", "requestId": "bk_xxx", "records": [],
  "preview": { "items": [
    { "index": 0, "amount": 35.0, "amountRaw": "35块", "type": 0,
      "categoryName": "餐饮", "categoryId": 1, "date": "2026-10-13",
      "dateExpr": null, "remark": null, "confidence": 0.9 } ] },
  "warnings": [] }
```

**确认请求**

```json
{ "message": "午饭35块", "clientMsgId": "uuid", "source": "voice",
  "previewId": "bk_xxxxx",
  "overrides": [ { "index": 0, "amount": 50 } ] }
```

> `overrides` 还支持 `categoryId` / `date` / `remark` / `type`，本次确认框只做金额编辑，其余字段预留。
> `previewId` 传预览响应里的 `requestId`；服务端命中预览缓存则复用解析结果、跳过第二次 LLM。

## 8. 已知取舍与限制

1. **预览必跑一次 LLM，确认不再跑（已优化）**：预览是「自动弹框」的必要成本，无法省。确认原先会**再解析一次**，现已通过 `previewId` + 服务端进程内 TTL 缓存复用预览结果，**确认路径只剩 DB 写入**（十来个毫秒级往返：幂等查询 / 配额 / 占位 INSERT / records INSERT / 日志 UPDATE / 会话消息 INSERT / commit）。缓存口径：TTL 300s（与弱幂等窗口对齐）、容量上限 500 条、键校验 `user_id` + `message`、读取返回深拷贝。未命中一律回退重新解析。
2. **非消费消息多一次解析**：每条聊天消息都会先跑一次记账预览再降级对话，多一次模型调用。这是「自动弹框」的必然代价，已由 20 次/分的预览限流兜底。
3. **缓存是进程内存态**：多 worker 部署时各进程独立缓存，命中率下降（表现为「有时快有时慢」），但**不影响正确性**。与项目现有的配额 / 并发槽 / 各类限流器同生命周期约束，生产应换 Redis。
4. **多笔中缺金额的条目**：确认框强制补全，因此不会触发服务端「跳过缺金额条目」的静默丢弃路径。
5. **限流为进程内滑动窗口**：与既有 FAQ / 语音限流一致，多 worker 部署时各进程独立计数，生产应换 Redis。
