# 02 · 数据库设计（MySQL 单库）

> 可执行单一事实来源：**`sql/init_mysql.sql`**（可直接执行、可重复执行）。本文档与之一一对应，字段口径不一致时**以脚本为准**。
> 依据源码：`entity/User.java`、`entity/Category.java`、`entity/Record.java`、`chatbot-server/db.ts`（建表与字段）、`chatbot-server/index.ts`（FAQ 种子）、`fast_backend/models/*.py`（现有 SQLAlchemy 模型）。
> 结论前置：AI 会话数据由 sql.js 内存库**合并进 MySQL 同一库**（ADR D1）。共 **9 张表** —— 业务 4 表（`users` / `user_token` / `categories` / `records`）+ AI 4 表（`sessions` / `messages` / `feedback` / `faq`）+ 自然语言记账日志 1 表（`ai_bookkeeping_logs`），统一 InnoDB / utf8mb4 / utf8mb4_general_ci。

---

## 0. 表名与字段口径（务必先读）

项目里曾并行存在**两套口径**：旧 Java/文档版（单数表名、`create_time`、`record_date`、`category.type` 为 0/1）与现有代码版（`fast_backend/models/`，复数表名、`created_at`、`date`、`type` 统一 1/2）。本设计**折中定稿**如下，不再变更：

| 项 | 定稿口径 | 说明 |
|----|----------|------|
| 业务表名 | **复数**：`users` / `user_token` / `categories` / `records` | 随 `fast_backend/models/` |
| AI 表名 | **单数**：`sessions` / `messages` / `feedback` / `faq` | 随旧 Express/sql.js 与 05 接口文档 |
| 业务表时间列 | `created_at` / `updated_at`（`DATETIME`） | 旧库为 `create_time` / `update_time`，迁移需列名映射 |
| AI 表时间列 | `created_at` / `updated_at` / `deleted_at` / `timestamp`（**`BIGINT` 毫秒**） | 前端 `Date.now()` 直接比对，**不可改 DATETIME** |
| `type` 语义 | 统一 **0=支出 / 1=收入** | `categories.type` 与 `records.type` 同一套。**前端硬约束，不可改**（见下方说明） |
| 金额列名 | `records.amount`，`DECIMAL(10,2)` | 禁止 float/double 存钱 |
| 日期列名 | `records.date`（`DATE`） | 旧库为 `record_date` |
| 系统预设分类 | `categories.user_id IS NULL` | 旧库写法是 `0`，但 `0` 不是 `users` 里的 id，建了外键就插不进去 |
| 删除语义 | 用户可软删（`records.status=0`）；分类删除受外键 `RESTRICT` 约束 | 见 §2.4 与「已知行为变更」 |
| 外键 | **建立真实 `FOREIGN KEY` 约束**，共 11 条 | 见 §6 |

### ⚠️ `type` 为什么必须是 0=支出 / 1=收入

这是**前端硬约束**（00 §2.4「前端零改动」），不是可选项。已核实的前端读法：

| 位置 | 代码 | 若改成 1/2 的后果 |
|---|---|---|
| `pages/Records.jsx` | `expenseCategories = categories.filter(c => c.type === 0)` | 支出分类**全被过滤掉**，记账页选不到支出分类 |
| `pages/Records.jsx` | `categoryType === 0 ? '-' : '+'`、`=== 0 ? danger : success` | 收支正负号与颜色**全部反向** |
| `pages/Records.jsx` | `activeType` tab `key: '0'`=支出、`key: '1'`=收入 | 收支切换 tab 全部错位 |
| `components/MainLayout.jsx` | `categories.filter(c => c.type === 0 / === 1)` | 全局记账弹窗分类分组错乱 |
| `pages/AdminRecords.jsx` | `r.categoryType === 0 ? '-' : '+'` | 管理端账单金额符号反向 |
| `pages/Dashboard.jsx` | `getCategoryStatistics({ type: 0 })` / `{ type: 1 }` | 统计图表收入支出互换 |
| uni-app `records/index` | `filter(e => e.type === this.formType)`（formType 0/1） | 移动端分类全空 |

仓库中 `fast_backend/models/*.py` 与 `fast_backend/docs/API文档_FastAPI.md` 曾写作「1 支出 / 2 收入」，属**未传导到前端的错误**，已一并改回 0/1。旧 Java 库的 `category.type` 本来就是 0/1，因此**存量数据无需转换**。

### 已知行为变更（相对旧 Java）

| # | 变更 | 影响面 |
|---|------|--------|
| B7′ | `records.category_id` 外键为 `ON DELETE RESTRICT`，**删除仍有账单的分类会失败（errno 1451）** | 旧行为是"删除成功、账单保留悬空 `category_id`"。要保留旧行为就不能建该外键（`sql/init_mysql.sql` 末尾「变体 B」） |
| — | `categories.user_id` 由 `0` 改为 `NULL` 表示系统预设 | 业务层判断从 `user_id == 0` 改为 `user_id IS NULL` |
| — | `users.role` 定为 **`TINYINT` 0/1**（0=普通用户，1=管理员） | **前端硬约束**：`AdminRoute.jsx` 用 `user.role !== 1` 拦管理后台、`AdminUsers.jsx` 用 `record.role === 1` 渲染标签，改字符串会整个进不去（详见 §0 说明） |

## 1. 全局规则

| 规则 | 取值 |
|------|------|
| 数据库 | `bookkeeping_book`，utf8mb4 / utf8mb4_general_ci，InnoDB |
| 主键 | 业务表自增 `BIGINT`；AI 会话/消息/反馈主键为**业务字符串 ID**（`session_xxx`/`msg_xxx`/`feedback_xxx`），用 `VARCHAR(64)` |
| 时间 | 业务表 `DATETIME`（无小数秒）；AI 会话/消息/反馈 **`BIGINT` 毫秒**（0 值语义见各表） |
| 金额 | `DECIMAL(10,2)`；禁止 float/double 存钱 |
| 列名 | 库表 snake_case；对外 JSON 由 Pydantic camelCase 序列化（见 03） |
| 自动填充 | 原 MyBatis-Plus `MetaObjectHandler` 自动写 `create_time/update_time`；现**统一交由 DDL 的 DEFAULT / ON UPDATE** 处理（见 §4） |
| 外键 | 全部建真实约束；删用户走 `ON DELETE CASCADE` 级联清理 |
| 字符集 | 所有表显式 `DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci` |

> ⚠️ 现有库（Spring Boot 老库）结构与本文档 DDL **不一致**（表名大小写、时间列名、`record_date`、`type` 语义、无 `user_token`）。执行前请按 §5「核对清单」比对；**升级路径见 §5.1 列名映射表**。

## 2. 业务表（4 张）

### 2.1 `users`（来源 `User.java` + `fast_backend/models/user.py`）

用途：用户账号主表，全部业务数据的归属主体。几乎所有业务查询都带 `user_id = 当前用户` 实现多用户隔离。

```sql
CREATE TABLE IF NOT EXISTS `users` (
    `id`            BIGINT       NOT NULL AUTO_INCREMENT           COMMENT '用户 ID，主键',
    `username`      VARCHAR(50)  NOT NULL                          COMMENT '用户名，登录账号，全局唯一',
    `password`      VARCHAR(100) NOT NULL                          COMMENT '密码哈希（BCrypt，$2b$10$ 开头共 60 字符）',
    `nickname`      VARCHAR(50)  NULL     DEFAULT NULL             COMMENT '昵称，可为空',
    `avatar`        VARCHAR(200) NULL     DEFAULT NULL             COMMENT '头像相对路径，如 /uploads/avatars/xxx.png',
    `email`         VARCHAR(100) NULL     DEFAULT NULL             COMMENT '邮箱，可为空',
    `phone`         VARCHAR(20)  NULL     DEFAULT NULL             COMMENT '手机号，唯一，可为空',
    `role`          TINYINT      NOT NULL DEFAULT 0                COMMENT '角色：0=普通用户，1=管理员',
    `status`        TINYINT      NOT NULL DEFAULT 1                COMMENT '状态：0=禁用，1=启用',
    `last_login_at` DATETIME     NULL     DEFAULT NULL             COMMENT '最后登录时间',
    `created_at`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `updated_at`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_users_username` (`username`),
    UNIQUE KEY `uk_users_phone` (`phone`),
    KEY `idx_users_status` (`status`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT = '用户账号表';
```

字段对照：旧 Java `avatarUrl(→avatar_url)` 现为 `avatar`；新增 `nickname/email/phone/status/last_login_at`。
`role` 保持 **TINYINT 0/1**（0=普通用户，1=管理员），与旧库一致、**存量数据无需转换**。

### 2.2 `user_token`（来源 `fast_backend/models/user.py` → `UserToken`）

用途：记录已签发的登录令牌，支持令牌吊销与多端登录管理。服务端同时支持无状态 JWT，本表用于需要主动失效令牌的场景。

```sql
CREATE TABLE IF NOT EXISTS `user_token` (
    `id`         BIGINT       NOT NULL AUTO_INCREMENT           COMMENT '令牌 ID，主键',
    `user_id`    BIGINT       NOT NULL                          COMMENT '所属用户 ID',
    `token`      VARCHAR(255) NOT NULL                          COMMENT '令牌值（JWT 或随机串），唯一',
    `expires_at` DATETIME     NOT NULL                          COMMENT '过期时间',
    `created_at` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_user_token_token` (`token`),
    KEY `idx_user_token_user` (`user_id`),
    CONSTRAINT `fk_user_token_user` FOREIGN KEY (`user_id`)
        REFERENCES `users` (`id`) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT = '用户登录令牌表';
```

> 本表是现有代码版新增的，旧 Java 库没有。若继续用纯无状态 JWT，可以不建；建了也不影响既有流程。

### 2.3 `categories`（来源 `Category.java` + `fast_backend/models/category.py`）

用途：账单的分类字典。系统预设分类 `user_id IS NULL`（所有用户可见、不可被用户删除），用户自建分类 `user_id` 指向本人。其中支出类的「其他」是 AI 自然语言记账识别不出分类时的**兜底归属**。

```sql
CREATE TABLE IF NOT EXISTS `categories` (
    `id`         BIGINT      NOT NULL AUTO_INCREMENT           COMMENT '分类 ID，主键',
    `user_id`    BIGINT      NULL     DEFAULT NULL             COMMENT '归属用户 ID；NULL 表示系统预设分类',
    `name`       VARCHAR(50) NOT NULL                          COMMENT '分类名称，如 餐饮/交通/工资',
    `type`       TINYINT     NOT NULL                          COMMENT '收支类型：0=支出，1=收入',
    `icon`       VARCHAR(50) NULL     DEFAULT NULL             COMMENT '图标标识，可为空',
    `sort_order` INT         NOT NULL DEFAULT 0                COMMENT '排序值，越小越靠前',
    `status`     TINYINT     NOT NULL DEFAULT 1                COMMENT '状态：0=禁用，1=启用',
    `created_at` DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `updated_at` DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (`id`),
    KEY `idx_categories_user_type` (`user_id`, `type`),
    CONSTRAINT `fk_categories_user` FOREIGN KEY (`user_id`)
        REFERENCES `users` (`id`) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT = '收支分类表（user_id 为 NULL 表示系统预设）';
```

改动点（相对旧 Java）：新增 `icon/sort_order/status`；`user_id` 允许 NULL（旧库用 0 表示系统预设）。`type` 语义保持 **0=支出 / 1=收入 不变**（前端按此判断）。
> 「同一用户同一 type 下分类名唯一」的约束**未启用**（源码无查重逻辑）。若产品要求，取消脚本中 `uk_categories_user_name_type` 那行注释即可。

### 2.4 `records`（来源 `Record.java` + `fast_backend/models/record.py`）

用途：记账流水表，核心业务表。手工记账（`POST /api/records`）与 AI 自然语言记账（`POST /api/ai/bookkeeping`）最终都写入本表。

```sql
CREATE TABLE IF NOT EXISTS `records` (
    `id`          BIGINT        NOT NULL AUTO_INCREMENT           COMMENT '账单 ID，主键',
    `user_id`     BIGINT        NOT NULL                          COMMENT '所属用户 ID',
    `category_id` BIGINT        NOT NULL                          COMMENT '分类 ID',
    `type`        TINYINT       NOT NULL                          COMMENT '收支类型：0=支出，1=收入',
    `amount`      DECIMAL(10,2) NOT NULL                          COMMENT '金额，必须大于 0，最大 99999999.99',
    `date`        DATE          NOT NULL                          COMMENT '记账日期',
    `remark`      VARCHAR(200)  NULL     DEFAULT NULL             COMMENT '备注，可为空',
    `status`      TINYINT       NOT NULL DEFAULT 1                COMMENT '状态：0=已删除（软删），1=正常',
    `created_at`  DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `updated_at`  DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (`id`),
    KEY `idx_records_user_date` (`user_id`, `date`),
    KEY `idx_records_category` (`category_id`),
    KEY `idx_records_user_status_date` (`user_id`, `status`, `date`),
    CONSTRAINT `fk_records_user` FOREIGN KEY (`user_id`)
        REFERENCES `users` (`id`) ON DELETE CASCADE ON UPDATE CASCADE,
    CONSTRAINT `fk_records_category` FOREIGN KEY (`category_id`)
        REFERENCES `categories` (`id`) ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT = '记账流水表';
```

改动点（相对旧 Java）：列名 `record_date → date`；新增 `type`（**0=支出 / 1=收入**，冗余存储所选分类的类型，便于统计免 JOIN）与 `status`（软删）；`remark` 由 `VARCHAR(255)` 收窄为 `VARCHAR(200)`。

统计 SQL 提示：旧 Java 用 `YEAR(date)=? AND MONTH(date)=?`（函数包裹列，**索引失效**）。改用**日期区间** `date >= ? AND date < ?`（当月 `[当月1日, 次月1日)`），在 `idx_records_user_date` 上可命中索引（行为等价，见 04 §4.1）。

## 3. AI 相关表（5 张）

> 时间单位：`sessions` / `messages` / `feedback` 的时间列均为 **毫秒 `BIGINT`**（前端直接比对）。`deleted_at=0` 表示未删除，`>0` 存删除时的毫秒值。
> 字符串 ID 规则（前端不依赖格式但历史数据如此）：session `session_{ms}_{随机}`；message `msg_{ms}_{随机}`；feedback `feedback_{ms}_{随机}`（随机段对应 JS `substring(2,11)`，最长 9 位）。

### 3.1 `sessions`（AI 对话会话，软删）

```sql
CREATE TABLE IF NOT EXISTS `sessions` (
    `id`         VARCHAR(64) NOT NULL                          COMMENT '主键，格式 session_{毫秒}_{随机≤9位}',
    `user_id`    BIGINT      NULL     DEFAULT NULL             COMMENT '归属用户 ID；NULL 表示历史遗留无主数据',
    `title`      VARCHAR(50) NOT NULL                          COMMENT '会话标题，默认「新对话」',
    `auto_title` TINYINT     NOT NULL DEFAULT 1                COMMENT '标题是否可被 AI 覆盖：1=可覆盖，0=用户已重命名锁定',
    `created_at` BIGINT      NOT NULL                          COMMENT '创建时间（毫秒时间戳）',
    `updated_at` BIGINT      NOT NULL                          COMMENT '更新时间（毫秒时间戳）',
    `deleted_at` BIGINT      NOT NULL DEFAULT 0                COMMENT '软删标记：0=未删除，>0=删除时的毫秒时间戳',
    PRIMARY KEY (`id`),
    KEY `idx_sessions_user` (`user_id`, `deleted_at`, `updated_at`),
    CONSTRAINT `fk_sessions_user` FOREIGN KEY (`user_id`)
        REFERENCES `users` (`id`) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT = 'AI 对话会话表（时间列为毫秒时间戳）';
```

> ⚠️ 现有代码 `fast_backend/models/chat.py` 里表名是 `chat_sessions`，且用 `TimestampMixin`（`DATETIME`）且**缺 `auto_title` / `deleted_at`**。这与前端「毫秒戳比对 + 相对时间格式化 + 标题自动生成后锁定」直接冲突，采用本设计后**必须同步改该模型文件**。

### 3.2 `messages`

```sql
CREATE TABLE IF NOT EXISTS `messages` (
    `id`         VARCHAR(64) NOT NULL                          COMMENT '主键，格式 msg_{毫秒}_{随机≤9位}',
    `session_id` VARCHAR(64) NOT NULL                          COMMENT '所属会话 ID',
    `role`       VARCHAR(16) NOT NULL                          COMMENT '角色：user=用户，assistant=AI',
    `content`    TEXT        NOT NULL                          COMMENT '消息正文',
    `timestamp`  BIGINT      NOT NULL                          COMMENT '发送时间（毫秒时间戳）',
    PRIMARY KEY (`id`),
    KEY `idx_messages_session_ts` (`session_id`, `timestamp`),
    CONSTRAINT `fk_messages_session` FOREIGN KEY (`session_id`)
        REFERENCES `sessions` (`id`) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT = 'AI 对话消息表（时间列为毫秒时间戳）';
```

### 3.3 `feedback`

```sql
CREATE TABLE IF NOT EXISTS `feedback` (
    `id`         VARCHAR(64) NOT NULL                          COMMENT '主键，格式 feedback_{毫秒}_{随机≤9位}',
    `message_id` VARCHAR(64) NOT NULL                          COMMENT '被评价的消息 ID',
    `rating`     TINYINT     NOT NULL                          COMMENT '评分，1~5',
    `comment`    TEXT        NULL                              COMMENT '文字反馈内容，可为空',
    `timestamp`  BIGINT      NOT NULL                          COMMENT '反馈时间（毫秒时间戳）',
    PRIMARY KEY (`id`),
    KEY `idx_feedback_message` (`message_id`),
    CONSTRAINT `fk_feedback_message` FOREIGN KEY (`message_id`)
        REFERENCES `messages` (`id`) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT = 'AI 回复反馈表（时间列为毫秒时间戳）';
```

> ⚠️ 本表**没有 `user_id`**（随旧 Express 结构），因此无法按用户维度隔离反馈。如需「谁反馈的」分析，需新增 `user_id` 列并同步 05 / 08。
> ⚠️ 注意 `TEXT` 列**不能带 `DEFAULT`**（MySQL 限制），故 `comment` 只写 `NULL`。

### 3.4 `faq`（含 8 条种子数据）

```sql
CREATE TABLE IF NOT EXISTS `faq` (
    `id`       INT         NOT NULL AUTO_INCREMENT           COMMENT '主键',
    `question` TEXT        NOT NULL                          COMMENT '问题',
    `answer`   TEXT        NOT NULL                          COMMENT '回答',
    `category` VARCHAR(50) NOT NULL                          COMMENT '分类标签，如 记账操作/账单查询',
    -- `embedding` TEXT     NULL                              COMMENT '向量（JSON 数组）；启用后可持久化向量',
    PRIMARY KEY (`id`),
    KEY `idx_faq_category` (`category`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT = 'FAQ 知识库表';
```

默认**不建 `embedding` 列**，向量在服务启动时内存构建（`rebuild` 同样只重建内存索引）。若希望向量持久化以加快启动，取消该行注释即可。

### 3.5 `ai_bookkeeping_logs`（自然语言记账日志 / 幂等 / 追问草稿）

> 对应能力见 **05 §6**（接口）与 **06 §11**（解析链）。
> 用途三合一：① 幂等去重；② 追问草稿暂存；③ "AI 记账 → 用户修改/删除"的审计与纠错样本。
> 时间单位：与业务表一致用 **DATETIME**（本表服务于 `records` 写入，不涉及前端毫秒戳语义）。

```sql
CREATE TABLE IF NOT EXISTS `ai_bookkeeping_logs` (
    `id`            BIGINT       NOT NULL AUTO_INCREMENT           COMMENT '主键',
    `request_id`    VARCHAR(64)  NOT NULL                          COMMENT '对外请求 ID，格式 bk_{毫秒}_{随机}',
    `user_id`       BIGINT       NOT NULL                          COMMENT '发起用户 ID',
    `session_id`    VARCHAR(64)  NULL     DEFAULT NULL             COMMENT '关联的 AI 会话 ID，可为空',
    `message_id`    VARCHAR(64)  NULL     DEFAULT NULL             COMMENT '关联的消息 ID，可为空',
    `client_msg_id` VARCHAR(64)  NULL     DEFAULT NULL             COMMENT '客户端幂等键（UUID）；NULL 表示不启用强幂等',
    `dedup_hash`    CHAR(64)     NOT NULL                          COMMENT 'SHA256(user_id|归一化文本)，用于弱幂等窗口去重',
    `raw_text`      VARCHAR(500) NOT NULL                          COMMENT '用户原始消息文本',
    `intent`        VARCHAR(20)  NOT NULL                          COMMENT '意图：bookkeeping/amend/delete/query/chitchat',
    `action`        VARCHAR(20)  NOT NULL                          COMMENT '处理结果：created/clarify/ignored/duplicate/preview/amend/delete/error',
    `parse_json`    JSON         NULL                              COMMENT 'LLM 抽取出的原始解析结果（06 §11.1 结构）',
    `record_ids`    JSON         NULL                              COMMENT '本次入账的 records.id 数组，如 [128,129]',
    `error_msg`     VARCHAR(200) NULL     DEFAULT NULL             COMMENT '失败原因（仅内部记录，不回显给前端）',
    `status`        TINYINT      NOT NULL DEFAULT 1                COMMENT '状态：0=草稿待追问，1=已处理，2=已回滚',
    `parent_id`     BIGINT       NULL     DEFAULT NULL             COMMENT '指向原日志 ID（追问续写 / 修改 / 撤销）',
    `created_at`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `updated_at`    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_abk_request_id` (`request_id`),
    UNIQUE KEY `uk_abk_client_msg` (`user_id`, `client_msg_id`),
    KEY `idx_abk_dedup` (`user_id`, `dedup_hash`, `created_at`),
    KEY `idx_abk_user_recent` (`user_id`, `created_at`),
    KEY `idx_abk_session` (`session_id`, `id`),
    KEY `idx_abk_parent` (`parent_id`),
    CONSTRAINT `fk_abk_user` FOREIGN KEY (`user_id`)
        REFERENCES `users` (`id`) ON DELETE CASCADE ON UPDATE CASCADE,
    CONSTRAINT `fk_abk_session` FOREIGN KEY (`session_id`)
        REFERENCES `sessions` (`id`) ON DELETE SET NULL ON UPDATE CASCADE,
    CONSTRAINT `fk_abk_message` FOREIGN KEY (`message_id`)
        REFERENCES `messages` (`id`) ON DELETE SET NULL ON UPDATE CASCADE,
    CONSTRAINT `fk_abk_parent` FOREIGN KEY (`parent_id`)
        REFERENCES `ai_bookkeeping_logs` (`id`) ON DELETE SET NULL ON UPDATE CASCADE
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_general_ci COMMENT = 'AI 自然语言记账日志表（幂等 / 追问草稿 / 审计）';
```

实现要点：

| 项 | 规则 |
|---|---|
| 幂等 | `uk_abk_client_msg` 强幂等（不过期）；`idx_abk_dedup` + 300s 窗口弱幂等（05 §6.1.5） |
| 并发 | 靠唯一键冲突兜底，**不要**"先 SELECT 再 INSERT" |
| 草稿 | `status=0` 且 `created_at` 在 30 分钟内有效；被续写后原日志置 `status=1`，新日志 `parent_id` 指回它 |
| 回滚 | 用户删除记录 → 新日志 `action='delete'`、`parent_id` 指向原日志，原日志 `status=2` |
| 查询最近一笔 | `WHERE user_id=? AND action='created' AND status=1 [AND session_id=?] ORDER BY id DESC LIMIT 1`（05 §6.4） |
| 清理 | 可复用 07 §1 的定时清理思路；`status=0` 草稿超 7 天可物理清除 |

> ⚠️ `client_msg_id` 允许 NULL，但 MySQL 唯一索引对多行 NULL 不冲突——这正是"未传幂等键时不触发强幂等"的预期行为，勿改成 NOT NULL。
> ⚠️ `parse_json` / `record_ids` 是 `JSON` 类型，**不能带 `DEFAULT`**，故只写 `NULL`。

## 4. 自动填充等价方案（替换 MyBatis-Plus MetaObjectHandler）

原 Java 行为：

```java
// MyMetaObjectHandler：insert 填 createTime+updateTime；update 填 updateTime
// 且 UserMapper 手工 SQL 中 update_time = NOW() 显式更新
```

FastAPI 实现策略（二选一，推荐 A）：

- **方案 A（DB 层）**：DDL 已含 `DEFAULT CURRENT_TIMESTAMP` 与 `ON UPDATE CURRENT_TIMESTAMP`，ORM 插入时**不传** `created_at/updated_at` 即可，简单且与手工 SQL 行为一致。
- **方案 B（应用层）**：SQLAlchemy `mapped_column(default=..., onupdate=...)`。适合需要应用时钟的场景，但需注意与 DB `NOW()` 可能存在毫秒差异，无必要不采用。

ORM 建模建议（`fast_backend/models/base.py` 已有 `IdMixin` / `TimestampMixin`），业务表时间列为 `datetime`，AI 表时间为 `int`（毫秒）：

```python
from datetime import datetime
from sqlalchemy import BigInteger, DateTime, func
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column


class Base(DeclarativeBase):
    pass


class IdMixin:
    """自增主键：统一 BIGINT，勿在子类重复声明（否则外键两侧类型会不一致，MySQL 报 errno 3780）"""
    id: Mapped[int] = mapped_column(BigInteger, primary_key=True, autoincrement=True, comment="主键 ID")


class TimestampMixin:
    """业务表：交给 DB DEFAULT / ON UPDATE，模型只读不写"""
    created_at: Mapped[datetime] = mapped_column(DateTime, server_default=func.now(), comment="创建时间")
    updated_at: Mapped[datetime] = mapped_column(DateTime, server_default=func.now(),
                                                onupdate=func.now(), comment="更新时间")
```

> ⚠️ 现有 `fast_backend/models/user.py` 有三处必须修：① `from sqlalchemy.testing.pickleable import User` 是 SQLAlchemy **测试内部模块**，生产导入必然失败；② `User` 重复声明 `id: Integer` 覆盖了 `IdMixin` 的 `BigInteger`，与 `categories.user_id`/`records.user_id` 类型不一致；③ `UserToken` 类整体多缩进一层。

| 旧库（Spring Boot） | 新库（本设计） | 处理方式 |
|---|---|---|
| `user` | `users` | 表名加 s；`avatar_url → avatar`；新增 `nickname/email/phone/status/last_login_at` |

--       records.type 是新增列，直接从所属分类的类型回填。

    CHANGE COLUMN `avatar_url` `avatar` VARCHAR(200) NULL COMMENT '头像相对路径',

-- 第 1 步：分类
ALTER TABLE `categories`
    CHANGE COLUMN `create_time` `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHANGE COLUMN `update_time` `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    MODIFY COLUMN `type` TINYINT NOT NULL COMMENT '收支类型：0=支出，1=收入',
    MODIFY COLUMN `user_id` BIGINT NULL DEFAULT NULL COMMENT 'NULL 表示系统预设分类',
    ADD COLUMN `icon` VARCHAR(50) NULL DEFAULT NULL COMMENT '图标标识',

## 6. 外键与关系总览

| # | 外键约束 | 从表.列 → 主表.列 | 关系 | 删除行为 |
|---|---|---|---|---|
| 1 | `fk_user_token_user` | `user_token.user_id` → `users.id` | N : 1 | CASCADE |
| 2 | `fk_categories_user` | `categories.user_id` → `users.id` | N : 1 | CASCADE |
| 3 | `fk_records_user` | `records.user_id` → `users.id` | N : 1 | CASCADE |
| 4 | `fk_records_category` | `records.category_id` → `categories.id` | N : 1 | **RESTRICT** |
| 5 | `fk_sessions_user` | `sessions.user_id` → `users.id` | N : 1 | CASCADE |
| 6 | `fk_messages_session` | `messages.session_id` → `sessions.id` | N : 1 | CASCADE |
| 7 | `fk_feedback_message` | `feedback.message_id` → `messages.id` | N : 1 | CASCADE |
| 8 | `fk_abk_user` | `ai_bookkeeping_logs.user_id` → `users.id` | N : 1 | CASCADE |
| 9 | `fk_abk_session` | `ai_bookkeeping_logs.session_id` → `sessions.id` | N : 1 | SET NULL |
| 10 | `fk_abk_message` | `ai_bookkeeping_logs.message_id` → `messages.id` | N : 1 | SET NULL |
| 11 | `fk_abk_parent` | `ai_bookkeeping_logs.parent_id` → 自身 `id` | 1 : N（自关联） | SET NULL |

关系归纳：

```
users ─1:N─> categories / records / user_token / sessions / ai_bookkeeping_logs
categories ─1:N─> records
sessions ─1:N─> messages ─1:N─> feedback
ai_bookkeeping_logs ─自关联─> ai_bookkeeping_logs (parent_id)
faq                          独立字典表，无外键
```

- **一对一**：本系统无 1:1 关系。
- **多对多**：本系统无 N:M 关系，因此**不需要中间表**。
- 若后续引入「账单标签」等多值属性，才需要 `tags` + `record_tags` 中间表。

> 设计约定提醒：若你的数据库与 §2/§3 DDL 不一致，后续文档中的 SQL/SQLAlchemy 写法以**列名（snake_case）**与**语义**为准，字段取值（如 `type` 1/2）不受表名影响。
