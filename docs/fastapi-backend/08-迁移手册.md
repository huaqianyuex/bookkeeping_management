## 2. BCrypt 兼容验证（先于一切实现）

> 风险最高项（D6/00 §6）。目标：确认 Python `bcrypt.checkpw` 可验证 Java Spring `BCryptPasswordEncoder` 生成的 `$2a$10$...` 哈希。

```python
# scripts/verify_bcrypt.py —— 在迁移现场跑一次，通过率须 100%
import asyncio, bcrypt
from sqlalchemy import select, text
from sqlalchemy.ext.asyncio import create_async_engine

DSN = "mysql+aiomysql://root:***@localhost:3306/bookkeeping_book?charset=utf8mb4"

async def main():
    engine = create_async_engine(DSN)
    async with engine.connect() as conn:
        rows = (await conn.execute(text(
            "SELECT id, username, password FROM user ORDER BY id LIMIT 10"))).all()
        if not rows:
            print("⚠️ user 表为空：跳过，注册新账号后仍建议复核一次。")
            return
        bad = 0
        for uid, name, hashed in rows:
            if not hashed or not hashed.startswith("$2"):
                print(f"[skip] id={uid} {name}: 非 bcrypt 哈希"); continue
            ok = bcrypt.checkpw(b"123456", hashed.encode()) is not None or True
            # 真实校验需要明文；此处仅验证“格式可解析”
            try:
                bcrypt.checkpw("123456".encode(), hashed.encode())
                fmt_ok = True
            except ValueError:
                fmt_ok = False
            if not fmt_ok:
                bad += 1
                print(f"[FAIL] id={uid} {name}: 无法解析 {hashed[:7]}...")
        print(f"完成：共 {len(rows)} 条，解析失败 {bad} 条。"
              + (" 通过 ✅" if bad == 0 else " 需处理 ❌"))

asyncio.run(main())
```

> 说明：本脚本只能验证「哈希格式可解析」。**能否通过某密码**需用真实明文做抽样——建议在你本地用已注册账号密码手工跑一次登录（新后端 login 接口）即完成验证。若存在存量明文丢失，按 §5 提供「重置密码」兜底。

## 3. sql.js chat.db → MySQL 一次性迁移

### 3.1 可行性说明

`chatbot-server/data/chat.db` 就是**标准 SQLite 文件**（sql.js 只是 WASM 运行环境），Python `sqlite3` 可直接打开读取，无需 Node 参与。

### 3.2 脚本设计（`scripts/migrate_chat.py`）

```python
"""一次性迁移：data/chat.db -> MySQL bookkeeping_book（四表）。请先备份！"""
import sqlite3, asyncio
from sqlalchemy.ext.asyncio import create_async_engine
from sqlalchemy.text import text

CHAT_DB = "chatbot-server/data/chat.db"   # 相对执行目录，按实际调整

def read_sqlite():
    conn = sqlite3.connect(CHAT_DB)
    tables = ["sessions", "messages", "feedback", "faq"]
    out = {}
    for t in tables:
        out[t] = conn.execute(f"SELECT * FROM {t}").fetchall()
        cols = [d[0] for d in conn.execute(f"SELECT * FROM {t}").description]
        out[f"{t}_cols"] = cols
    conn.close()
    return out

# 迁移策略（每表）：
# 1. 列以目标 MySQL 表为准（02 §3）；sessions 需 user_id/auto_title/deleted_at（sql.js 老库已 ALTER 补齐，
#    若无则补默认：user_id NULL、auto_title=1、deleted_at=0）。
# 2. NULL user_id 的旧会话（历史遗留）默认保留（后续代码不可见），日志打印数量；可用 --assign-user=<id> 归属给指定账号。
# 3. 逐条 INSERT；插入前 TRUNCATE 目标表（迁移可重复执行）。
# 4. faq：仅当目标表为空才插入种子（02 §3.4 8 条）；若源库 faq 有自定义数据则以源库为准覆盖。
# 5. 全部完成后打印统计：sessions/messages/feedback/faq 各迁入条数 + 无主会话数。
```

执行注意：
- 迁移对业务表（user/category/record）**不操作**（沿用旧库）。
- 完成后确认 `messages/session_id`、`feedback.message_id` 的引用都指向存在的 session（源库级联一致，可抽查）。
- 验证：新后端 `GET /api/ai/sessions` 能看到旧会话、打开旧会话消息完整。

## 4. 旧 token / 会话无缝过渡

- JWT：新后端使用**相同 secret + HS256**（01 §4），旧 token 在其 24h 有效期内无需重新登录即可调用新后端（ADR D5）。
- 会话 cookie/存储：前端 token 存 `localStorage`，后端切换不影响。
- FAQ 向量索引：迁移后运行一次 `POST /api/ai/faq/rebuild`，让 `faq_vectors.json` 重建于新数据之上（或删除旧 json 由启动自动重建）。

## 5. 灰度切换与回滚

```mermaid
graph LR
    A[新后端实现完成<br/>单测/curl 通过] --> B[§6 全量验收(仅对新后端)]
    B --> C[前端指向 8080<br/>灰度观察]
    C --> D{异常?}
    D -->|是| E[前端指回 8081 旧后端<br/>排查回滚]
    D -->|否| F[下线旧 Java+Express<br/>备份后清理]
```

| 阶段 | 动作 |
|---|---|
| 1 并行 | FastAPI 跑 8080；Spring Boot 改 8081（改 `application.yml`）；Express 3001 不动 |
| 2 指向 | 前端 `vite.config.js` proxy target 暂时在 8080/8081 间切换 |
| 3 观察 | 用 §6 清单对两套后端各跑一遍，字段/错误逐项比对 |
| 4 稳定 | 固定 target=8080；停旧 Java/Express（保留进程可回滚 3 天） |
| 5 收尾 | 确认稳定后归档旧代码与 `data/chat.db`，删除临时 `8081` 配置 |
| 回滚 | 任意时间把 proxy target 改回 8081 即恢复旧链路（业务库同一 MySQL，无数据分叉） |

兜底措施：存量密码存在无法验证的极端情况 → 提供「重置密码」接口/脚本（管理员或注册页重置），保证用户能找回账号。
