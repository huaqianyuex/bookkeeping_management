## 1. 定时任务：物理清除过期软删会话（`app/tasks/purge.py`）

原 JS 行为：

```js

// cutoff = now - 7天；找出 deleted_at > 0 且 < cutoff 的会话 → 级联物理删除 messages/feedback/sessions
```

FastAPI（APScheduler `AsyncIOScheduler`）等价实现：

```python

    # SELECT id FROM sessions WHERE deleted_at > 0 AND deleted_at < :cutoff
    # 级联删除：feedback(message_id in ...) -> messages(session_id in ...) -> sessions
    return deleted_count


def start_scheduler() -> None:
    """仅在 uvicorn 单 worker / 主进程调用（见 lifespan 与 §3.2）。"""
    global scheduler
    s = get_settings()
    scheduler = AsyncIOScheduler()
    scheduler.add_job(purge_expired_sessions, "interval",
                      hours=s.purge_interval_hours, next_run_time=datetime.now())  # 启动即跑一次
    scheduler.start()


def stop_scheduler() -> None:
    if scheduler:
        scheduler.shutdown(wait=False)
```

挂载位置：`app/main.py` lifespan 内 `start_scheduler()`（启动后立刻执行一次与每 6h 对齐 JS）。

### 多 worker 防重（红线）

`gunicorn -w N`（N>1）会拉起 N 个 scheduler → **同一会话可能被多个 worker 同时物理删除**。处理：
- 推荐 N=1（内存与任务都简单，毕设场景足够）；
- 若必须多 worker：用环境变量（如 `ENABLE_SCHEDULER=1`）只让主 worker 启任务，或用 MySQL `GET_LOCK`/独立表做分布式锁。

## 3. 运行部署

### 3.1 本地开发（Windows，两个终端即可）

```powershell
# 终端 1：FastAPI（替代原 Java+Express 两个终端）
cd backend/fastapi-backend
.\.venv\Scripts\Activate.ps1
uvicorn app.main:app --reload --host 0.0.0.0 --port 8080

# 终端 2：前端（不变）
cd personal-ledger-frontend
npm run dev
```

> MySQL 仍须先启动（同原启动文档 Step1）。原「Step2 Java + Step3 Express」被上述单命令取代。

### 3.2 生产部署（Linux 服务器）

```bash
cd backend/fastapi-backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
# 内存收益前提：单 worker 全 async（ADR D3）
gunicorn app.main:app -k uvicorn.workers.UvicornWorker -w 1 -b 0.0.0.0:8080 \
  --timeout 300 --graceful-timeout 60 --access-logfile -
```

参数说明：`--timeout 300` 需覆盖长 SSE 空闲期（可配 keep-alive 处理）；若追求并发可用 `-w 2`（接受内存上升并注意 §1 防重与下面的「多 worker + SSE」提示）。

**多 worker + SSE 注意**：SSE 长连接会独占该 worker；`-w 1` 下并发 N 个对话会串行化 LLM 流——个人演示可接受，但若需要并发请在 2~4 worker 与内存之间权衡（00 已提示多 worker 将抵消内存收益）。

### 3.3 nginx（SSE 关键配置）

```nginx
server {
    listen 80;
    server_name ledger.example.com;

    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_buffering off;          # 关键：禁止缓冲，否则 SSE 全部延迟后一次性到达
        proxy_cache off;
        proxy_read_timeout 300s;
        add_header X-Accel-Buffering no;   # 与后端 SSE 响应头呼应（05 §2.2）
    }

    location /uploads/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_cache off;
    }
}
```

### 3.4 进程守护 / Windows 服务

- Linux：systemd unit（`ExecStart=/opt/ledger/backend/fastapi-backend/.venv/bin/gunicorn ...`）+ 日志重定向。
- Windows 开发机：无需守护，用新 `start-all.bat`（见 3.5）。


（路径 `%~dp0` 相对本脚本所在目录，请按实际放置调整。）

## 4. 灰度共存与回滚端口规划

迁移期间新老后端并行、前端无感切换：

| 进程 | 端口 | 角色 |
|---|---|---|
| FastAPI（新） | 8080 | 最终目标（前端代理指向它） |
| Spring Boot（旧） | 8081 | 灰度对照（改 `application.yml` server.port） |
| Express（旧） | 3001 | 仅被旧 Java 转发使用，保持不动 |

前端切换方式（无需改代码）：临时改 `vite.config.js` proxy target 在两个端口间切换，验证通过后固定 8080。切换步骤与 10 项验收清单见 08 §6。
