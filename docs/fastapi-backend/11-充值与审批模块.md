# 11 · 充值与审批模块（会员套餐直购 + 安全审批）

> **适用范围**：本模块仅在扩展版后端 `fast_backend -fwature-expansion-version` 实现（会员模块的完整实现载体，前端两端实际联调对象）；主后端 `fast_backend` 的会员骨架保持不动，后续需要时按本文档回移。
> **依赖**：会员模块（`docs/membership-plan.md`）——充值入账复用其 `user_membership` 叠加语义（`crud/membership.py::extend_membership_for_recharge`，source=2 充值购买）。
> **暂缓事项**：涉及**营业执照资质审核**的部分（真实微信支付/支付宝商户进件、商户号配置、资质材料上传与审核流程）本期不做，仅以支付网关抽象预留（见 §6）。其余充值功能与安全审批链路全部落地。
> **建表方式**：项目无 alembic，DDL 手写同步 `sql/init_mysql.sql`（表 13/14）与 `sql/create_tables_from_models.sql`。

## 0. 业务定位与术语

| 项 | 口径 |
|----|------|
| 业务模型 | **套餐直购**：月卡 30 天 / 季卡 90 天 / 年卡 365 天，支付成功即按会员体系叠加语义延期（`base = max(NOW, 现有 expires_at 且 tier==1)` + days） |
| 定价 | **服务端唯一定价源** `config/settings.py::RECHARGE_PLANS`；客户端只传套餐 ID，永不传金额/天数 |
| 支付 | **模拟支付网关**（pay_method=0）：服务端模拟收银台 + HMAC 签名回调，流程与真实渠道同构 |
| 审批 | **风险分层**：每笔订单走完整校验链并留痕；命中风控规则（金额阈值/频率/失败次数）→ 支付后转「待人工审批」，管理员在 React 管理端终审 |
| 订单快照 | `plan_name / days / amount` 下单时刻固化，套餐调价不影响历史订单对账 |

## 1. 订单状态机

```
                         ┌────────────────────────────────────────────┐
                         │          apply_payment_callback            │
                         │ （唯一入账入口：HMAC 验签 + 金额核对 + 行锁） │
                         └────────────────────────────────────────────┘
  0 待支付 ──支付成功·风控通过──→ 2 已支付（同事务：PAY_SUCCESS + EXTEND_MEMBERSHIP 审计 + 会员延期）
  0 待支付 ──支付成功·命中风控──→ 1 待审批（钱已收；管理员通过 → 2 / 拒绝 → 3）
  0 待支付 ──用户取消──────────→ 4 已取消
  0 待支付 ──超时（读/支付路径懒关闭）→ 5 已关闭
  1 待审批 ──管理员通过────────→ 2 已支付（同事务入账，reviewed_by/at/note 落库）
  1 待审批 ──管理员拒绝（原因必填）──→ 3 已拒绝（模拟渠道原路退回）

  终态集合 {2,3,4,5}；其余流转一律 400。所有流转与审计日志同一事务提交。
```

状态常量（`crud/recharge.py`，与 DDL/模型注释同口径）：`0=待支付 1=待审批 2=已支付 3=已拒绝 4=已取消 5=超时关闭`。

## 3. 安全审批链路（防绕过设计）

每一笔充值必须经过以下链路，缺一即不可能到账：

| # | 环节 | 实现 | 拦截的攻击 |
|---|------|------|-----------|
| ① | 登录态 + 归属校验 | 用户端点全部 `Depends(get_current_user)`；支付/取消按 `order_no + user_id` 双条件查单（跨用户一律 404，不暴露订单存在性） | 未登录下单、代付他人订单 |
| ② | 服务端定价 | 下单只收 `planId`，金额/天数取 `RECHARGE_PLANS` 快照 | 客户端篡改金额/天数（0.01 元买年卡） |
| ③ | 创建频率限流 | `SlidingWindowRateLimiter`（60s 内 ≥3 次 → 429，进程内滑动窗口） | 脚本批量造单刷审计/占名额 |
| ④ | 进行中订单幂等 | 同用户 `status=0` 订单数 ≥ `RECHARGE_MAX_PENDING_ORDERS` → 400（先懒关闭超时单再统计） | 堆积挂单绕过支付有效期 |
| ⑤ | 支付失败冷却 | `LoginThrottle` 变体：连续失败 ≥5 次 → 15 分钟冷却（429） | 暴力重试/探测风控阈值 |
| ⑥ | 回调验签 | `build_payment_event`：HMAC-SHA256(`order_no|amount|status`) 常数时间比较，**密钥只在服务端**；事件以 frozen dataclass 传入状态机（类型层面封死未验签入账） | 伪造"支付成功"回调（客户端无密钥） |
| ⑦ | 金额核对 | 回调金额 `Decimal` 比对订单应收，不符 → 拒绝受理 + `PAY_FAIL` 审计 | 网关侧改单 |
| ⑧ | 状态机 + 行锁 | 推进前 `SELECT ... FOR UPDATE`；终态幂等应答（重放无害，不重复入账）；非法流转 400 | 并发重复入账、跨状态越权流转 |
| ⑨ | 风控评估（支付时） | 单笔 ≥ `RECHARGE_MANUAL_REVIEW_AMOUNT` 或当日累计（已支付+待审批，按 DB 日期）≥ `RECHARGE_DAILY_REVIEW_AMOUNT` → 转 1 待审批；阈值不下发前端 | 大额拆单（日累计口径含待审批，拆单无效） |
| ⑩ | 人工终审 | 待审批订单仅 `get_current_admin`（role=1）可通过/拒绝；拒绝原因必填；通过/拒绝与会员延期、审计同事务 | 越权审批、无痕审批 |
| ⑪ | 全程留痕 | 每次流转一行审计（操作方/前后状态/IP/详情），append-only | 抵赖、无痕改单 |

> 单笔阈值与日累计阈值刻意**不下发前端**（防止探测后精准拆单）；用户端只展示"大额订单需人工审核"通用文案。

## 5. 接口规范（统一 `{code, message, data}` 信封）

### 5.1 用户侧 `/api/recharge`（均需登录）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/plans` | 套餐目录（服务端定价） |
| POST | `/orders` | 创建订单，body `{planId}`；成功返回订单快照；进行中订单已满 → 400 |
| POST | `/orders/{orderNo}/mock-pay` | 模拟收银台，body `{result: "success"\|"fail"}`；内部生成签名事件走同一回调路径；失败冷却中 → 429 |
| POST | `/orders/{orderNo}/cancel` | 取消待支付订单 |
| GET | `/orders` | 我的充值记录（分页 PageResult） |
| GET | `/orders/{orderNo}` | 订单详情（跨用户 404） |

创建响应示例：

```json
{
  "code": 200, "message": "订单已创建，请在 15 分钟内完成支付",
  "data": {
    "id": 1, "orderNo": "RCH20261006120000A1B2C3", "planId": "month",
    "planName": "月卡", "days": 30, "amount": "18.00",
    "status": 0, "statusText": "待支付", "payMethod": 0,
    "riskFlags": null, "paidAt": null, "reviewedAt": null, "reviewNote": null,
    "expiresAt": "2026-10-06T12:15:00", "createdAt": "2026-10-06T12:00:00"
  }
}
```

`GET /plans` 响应含 `benefits: {free, member}` 两档权益矩阵（来自 MEMBERSHIP_PLANS，camelCase 同 `_benefits` 映射），是用户端"充值前信息展示"（费用/有效期/权益对比/使用规则）的唯一数据源，前端禁止硬编码额度；有效期预览按叠加语义 `base = max(现在, 现有到期) + days` 由前端计算展示（展示用，入账以服务端为准）。

错误场景：`400 套餐不存在` / `400 操作过于频繁，请 N 秒后再试`（创建限流）/ `400 您已有待支付的订单…` / `429 支付尝试过于频繁…`（失败冷却）。

### 5.2 支付回调闸口 `POST /api/recharge/callback`（无需登录——签名即信任根）

请求体：`{orderNo, amount, status: "success"|"fail", sign}`，`sign = HMAC-SHA256(key, "orderNo|amount|status")`。

| 场景 | HTTP |
|------|------|
| 签名无效 / 非法 status / 篡改金额串 | **401**（永远到不了状态机） |
| 订单不存在 / 超时关闭 / 金额与应收不符 | 400（含审计留痕） |
| 重复回调（已支付/待审批） | 200 幂等应答，**不重复入账** |
| 成功且低风险 | 200 `支付成功，会员已延长 N 天`（同事务入账） |
| 成功且命中风控 | 200 `支付成功，订单已进入人工审核…`（status=1，待管理员放行） |

### 5.3 管理侧 `/api/admin/recharges`（均需管理员）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/` | 订单分页：`page/size/status/keyword`（keyword 匹配用户名/订单号/套餐名，LIKE 已 `escape_like` 防注入） |
| GET | `/{id}/logs` | 审计轨迹时间线（404 若订单不存在） |
| POST | `/{id}/approve` | 通过放行，body `{note?}`；同事务延期会员 |
| POST | `/{id}/reject` | 拒绝，body `{reason}` **必填**（schema 校验，422） |

错误场景：非管理员 403；非待审批状态操作 400；订单不存在 404。

## 7. 支付网关抽象与暂缓事项

- **已实现**：模拟网关（pay_method=0）——服务端生成签名事件 → `apply_payment_callback` 统一处理。真实渠道接入后只需实现渠道适配器：创建预付单 → 收银台 → 渠道回调打到 `/api/recharge/callback`（验签函数按渠道规则替换为 RSA 验签即可），状态机/审计/审批零改动。
- **暂缓（营业执照资质审核）**：真实微信支付/支付宝的商户进件、商户号/密钥配置、资质材料上传与审核流程。本期不做，接口与数据模型已预留 `pay_method` 维度。

## 9. 测试清单（`tests/test_recharge.py`，405 全绿的一部分）

- 签名/事件构造：roundtrip、篡改金额/订单号拒绝、非法 status 拒绝、frozen 事件不可改；
- 服务端定价：`/plans` 与 `RECHARGE_PLANS` 一致、价格 Decimal 正数可解析、未登录 401；
- 下单：未知套餐 400、金额快照口径（字符串）、进行中订单上限提示透传；
- 回调闸口：坏签名 401、**签名对但报文金额篡改 401**（闸口拦截）、合法签名进入状态机、业务失败 400；
- 模拟支付：归属校验 404、成功路径参数透传、失败路径 400、失败冷却真实触发；
- 审批：非管理员 403、拒绝原因必填 422、通过/拒绝参数与业务 400 透传、列表筛选/审计轨迹/404；
- 进程内防刷器（创建限流/失败冷却）已纳入 `conftest._reset_in_memory_throttles` 用例间清理。

**单测边界**：状态机流转/风控评估/审计写行的 DB 交互依赖真实 MySQL 事务与行锁，按项目约定（不连真库、monkeypatch crud）以路由参数透传 + 闸口逻辑为主；`manual_e2e_membership.py` 同款人工端到端验证可覆盖资金链路。

**实测补充（2026-10-06 联调发现）**：向 ORM 属性赋 `func.now()`（DB 时钟口径）并提交后，该属性在 flush 时过期；异步上下文里再序列化它会触发隐式懒加载，抛 `MissingGreenlet`（被包装为 `StatementError`，SQLAlchemyError 子类）→ 全局处理器返回 500「数据库操作失败」。已在入账/风控路径 commit 后 `db.refresh(row)` 重载解决；回移主后端时务必保留这两处 refresh。
