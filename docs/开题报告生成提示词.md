## 二、项目资料（唯一事实来源，写作时以此为准）

### 2.1 项目一句话概述

一套面向个人用户的智能记账管理系统，由 Web 管理端、跨端移动端与统一后端三部分组成：在传统记账（分类、账单、统计）能力之上，接入大语言模型提供流式智能问答、消费结构分析与预算规划能力，并把原「网关 + AI 微服务 + 独立内存数据库」的三进程架构重构为单个 FastAPI 全异步进程。

### 2.2 系统总体架构（三段式）

1. **客户端层**
   - Web 端：React 18 + Vite 5 + Ant Design 5 + axios + React Router 6，共 11 个页面（登录、注册、数据概览、账单管理、分类管理、个人信息、修改密码、AI 对话、管理后台概览、管理后台用户、管理后台账单）。
   - 移动端：uni-app（Vue 3）跨端工程，含登录、注册、数据概览、账单列表、账单增改、分类、个人中心、AI 对话、AI 历史会话等页面，可编译为 H5、微信小程序与 App。
2. **服务层**：单个 FastAPI 进程，`uvicorn` 启动，全链路 `async`；对外提供约 38 个 REST 接口（业务接口 24 个 + AI 接口 14 个，另含 `/api/health` 健康检查）。路由按资源划分为 user / category / record / statistics / admin / ai 六组。
3. **数据与外部服务层**：MySQL 8.0 单库（`bookkeeping_book`，InnoDB / utf8mb4，共 7 张表）；静态头像目录 `/uploads/avatars` 由后端 StaticFiles 挂载；大模型通过 OpenAI 兼容协议 httpx 异步流式调用（网关 `apihub.agnes-ai.com/v1`，对话模型 `agnes-2.5-flash`、分析模型 `agnes-2.0-flash`、向量模型 `text-embedding-3-small`）。

### 2.3 技术栈选型表

| 层次 | 技术 | 选型理由（写"研究方案"时可展开） |
|---|---|---|
| Web 前端 | React 18、Vite 5、Ant Design 5、axios、dayjs | 组件生态成熟，适合管理类中后台界面 |
| 移动端 | uni-app（Vue 3）、pinia | 一套代码覆盖 H5 / 小程序 / App，降低多端成本 |
| 后端框架 | FastAPI 0.115 + uvicorn | 原生异步、自动生成 OpenAPI 文档、Pydantic 数据校验 |
| ORM / 驱动 | SQLAlchemy 2.0（async）+ aiomysql | 全异步数据库访问，与 SSE 长连接共存不阻塞 |
| 数据校验 / 配置 | Pydantic 2 + pydantic-settings | 请求响应强类型校验，配置集中由 `.env` 管理 |
| 认证安全 | PyJWT（HS256）+ bcrypt | 无状态 JWT 鉴权；bcrypt 兼容 Spring 侧 `$2a$10$` 存量哈希 |
| AI 编排 | LangChain（langchain-openai）为主方案，openai SDK + httpx 为轻量对照方案 | 主方案便于链式编排与结构化输出绑定；轻量方案依赖更少 |
| 实时通信 | Server-Sent Events（StreamingResponse） | 单向流式输出场景下比 WebSocket 更轻，天然穿透 HTTP 基础设施 |
| 定时任务 | APScheduler（AsyncIOScheduler） | 过期软删会话的物理清理 |
| 数据库 | MySQL 8.0 | 事务与索引能力满足账务数据准确性要求 |
| 部署 | gunicorn + UvicornWorker + nginx | 生产环境进程守护与 SSE 反向代理 |

### 2.4 功能模块清单（九个模块）

1. **用户模块**：注册、登录、查询资料、修改资料、修改密码、头像上传（`multipart/form-data`，大小 ≤ 2MB，仅 JPG/PNG，上传成功自动清理旧头像）。
2. **收支分类模块**：按"支出 / 收入"两类管理用户自定义分类，支持新增、列表查询（可按类型过滤）、修改、删除。删除分类不级联删除历史账单。
3. **账单记录模块**：账单的新增、详情、修改、删除与分页列表；支持按分类、按月份（`yyyy-MM`）筛选，默认按 `record_date`、`create_time` 倒序；列表通过 LEFT JOIN 补全分类名称与类型。
4. **统计分析模块**：月度总览（本月收入、本月支出、本月结余）与分类占比统计（按金额倒序，占比保留 1 位小数、四舍五入）。
5. **AI 智能对话模块**：多轮会话的创建、列表（支持关键词搜索、按更新时间/创建时间排序、分页）、重命名、软删除、批量删除（单次上限 50 条）、消息读取；对话支持 SSE 流式输出，事件协议为 `data: {"type":"content"|"done"|"error"}`。
6. **消费分析模块**：接收自然语言查询，由服务端自动组装该用户的本月收支概况、支出 Top5 分类与上月对比数据，交给大模型按固定分析维度产出**结构化结果**（总结、总支出、分类趋势、关键洞察、可执行建议、储蓄率、消费健康度评级）。
7. **预算规划模块**：依据用户月收入与储蓄目标，结合历史消费数据，按 50/30/20 法则生成结构化预算方案（月预算总额、5–8 个分类限额及理由、储蓄目标、预算风险提示）。
8. **FAQ 知识库检索（RAG）模块**：内置 8 条记账领域问答种子数据，对问题与答案向量化后按余弦相似度检索（相似度阈值 0.5，取 Top 3）；向量服务不可用时自动降级为关键词检索，保证功能可用。
9. **管理后台模块**：用户列表与检索、用户详情、删除用户（事务内级联删除其账单与分类，禁止删除管理员）、批量删除用户、全站账单查询（按类型/月份/用户过滤）与批量删除、系统概览（用户数、账单数、收入总额、支出总额、分类数）、AI 会话统计（会话数、消息数、反馈数、平均评分）。

此外系统内含**对话记忆管理**：按"中文 × 0.75 + 英文词 × 1.3 + 数字串 × 0.5"估算 Token，在 2000 Token 预算内保留最近 6 条完整消息，更早内容压缩为摘要后送入模型。

### 2.5 数据库设计（MySQL 单库 7 表）

- 业务表 3 张：`user`（用户名唯一、密码存 BCrypt 哈希、角色 0 普通/1 管理员）、`category`（名称、类型 0 支出/1 收入、归属用户）、`record`（金额、备注、记账日期、归属用户与分类）。金额统一 `DECIMAL(10,2)` 禁止浮点存储；`record` 上建 `(user_id, record_date)` 与 `(category_id)` 索引。
- AI 表 4 张：`sessions`（会话，含 `auto_title` 标记是否允许 AI 覆盖标题、`deleted_at` 软删时间戳）、`messages`（消息，role 为 user/assistant）、`feedback`（评分与评论）、`faq`（知识库）。
- 时间语义刻意不统一：业务表用 `DATETIME` 输出 ISO 字符串；AI 会话相关表用**毫秒级 BIGINT**，以适配前端直接做时间戳比对与相对时间展示。

### 2.6 关键技术点（供"拟解决的关键问题"使用）

1. **异构多后端到单进程全异步的架构整合**。原系统为三进程：Spring Boot 承担网关并转发、Express 承载 AI 链、sql.js 以内存 SQLite 独立存放会话数据（全库常驻内存且需整体导出）。整合为单 FastAPI 进程后，AI 能力变为进程内调用，会话数据并入 MySQL。
2. **前端零改动的接口契约约束**。客户端已按既定路径、字段名与响应结构实现，后端重构不得更改；同时业务接口统一包裹 `{code,message,data}`，而 AI 接口必须返回裸 JSON，两套响应契约并存且分页结构不同（业务为 `records/total/pages/current/size`，AI 为 `items/total`）。
3. **SSE 流式输出的全链路异步化**。若任一环节使用同步阻塞调用，在单进程模型下并发会话将耗尽工作线程，导致整体不可用；因此数据库访问、模型调用、流式转发必须全部为异步。
4. **大模型结构化输出的可靠性**。需要模型稳定产出可被前端渲染的字段，采用 JSON 模式约束 + Pydantic 模型校验，校验失败即降级为错误响应而非脏数据入库。
5. **检索增强与降级的可用性**。向量检索依赖外部 Embedding 服务，需在服务不可用时自动切换关键词检索，避免整条问答链路失效。
6. **长对话的上下文成本控制**。Token 估算与历史摘要压缩，在有限上下文预算内兼顾回答质量与调用成本。
7. **多租户数据隔离与权限控制**。所有业务查询强制带当前用户条件，会话读取需校验归属与软删状态；管理员接口叠加角色校验。
8. **统计查询的性能与数据正确性**。将原本基于 `YEAR()/MONTH()` 函数的条件改写为可命中索引的日期区间条件；账单列表的分类补名由逐条查询优化为批量查询；占比计算统一舍入规则避免前端展示误差。

### 2.7 运行与部署

- 开发环境为 Windows，MySQL → 后端 → 前端依次启动，后端端口沿用 8080，前端开发服务器 5173 通过代理访问 `/api` 与 `/uploads`。
- 生产环境为 Linux，使用 gunicorn + UvicornWorker 部署；nginx 反向代理需关闭响应缓冲，否则 SSE 会被整体缓存后一次性下发，流式效果丧失。
- 定时清理任务仅在单 worker 下启动，避免多 worker 重复删除同一批数据。

## 四、写作规范

- **总字数 4500–6000 字**（不含参考文献）。
- 各章字数建议配比：选题背景与意义 600–800 字；研究现状 1000–1300 字；研究目标内容与关键问题 900–1100 字；研究方案与技术路线 1300–1600 字；特色与创新点 300–400 字；进度安排 150–250 字；预期成果 150–250 字。
- **研究现状必须"述评结合"**。每篇文献不能只罗列结论，要按"研究做了什么 → 解决了什么 → 还有什么没解决"的结构展开，并自然引出本文切入点。
- **三处内容不得重复**：研究内容写"做什么"，关键技术点写"难在哪、怎么破"，创新点写"与已有工作的差异"。
- 术语首次出现给全称：SSE（Server-Sent Events，服务器发送事件）、RAG（Retrieval-Augmented Generation，检索增强生成）、LLM（Large Language Model，大语言模型）、JWT（JSON Web Token）。
- 章节内可用小标题分点，但避免整章变成条目清单，需有成段论述。
- 涉及系统功能时统一使用"本系统"，不使用"我的系统""我们这个项目"。
