# AI 对话系统 Agent 化评估

> 核查对象：`fast_backend -fwature-expansion-version`（功能演进版，前端默认联调的主线）
> 核查日期：2026-10-11
> 核查方式：逐文件通读真实代码 + 全局 grep 验证，所有结论均可按「文件:行号」复核

---

## 0. 一句话结论

**当前系统不是 Agent，而是一个「带 LLM 的规则化对话系统」（LLM-augmented chatbot + 固定流水线）。**

它已经具备 Agent 的**大脑、安全约束、短期记忆**三块，也具备**环境感知与控制循环的雏形**，
但**完全缺失「工具调用」与「规划」**这两块决定性的能力——而这恰恰是「Chatbot」与「Agent」的分水岭。

判定依据（最关键的一条）：

| 判据 | Agent | 当前系统 |
|---|---|---|
| LLM 是否自主决定「下一步做什么」 | 是（自主规划 + 选工具） | **否**——流程由代码硬编码，LLM 只在固定位置做单次抽取/生成 |
| 是否具备「行动 → 观察 → 再决策」闭环 | 是 | **否**——单次调用即返回，无工具、无多轮观察 |
| 能力边界是否可被外部扩展 | 是（加工具即加能力） | **否**——加能力必须改路由代码 |

系统里的 LLM 更像一个**「高精度解析器 + 文本生成器」**，而不是**决策主体**。
真正在编排流程的是 `routers/ai.py` 里那 1300 行 Python。

### 1.1 大脑（LLM）—— ✅ 已具备

**实现位置**：`ai/llm.py`（68 行）

| 工厂函数 | 模型 | 温度 | 特殊点 |
|---|---|---|---|
| `get_chat_llm(premium=False)` | `CHAT_MODEL`（agnes-2.5-flash） | 0.7 | 进程内单例；`streaming=True` |
| `get_chat_llm(premium=True)` | `CHAT_MODEL_PREMIUM` | 0.7 | 会员走高级模型，未配置时回退 |
| `get_analyze_llm()` | `ANALYZE_MODEL`（agnes-2.0-flash） | 0 | 配合 `with_structured_output` 保证稳定 |
| `get_embeddings()` | `text-embedding-3-small` | — | 函数内延迟 import，FAQ 未启用时不付加载成本 |

**做得好的地方**（`ai/llm.py:16-31` 的注释写得很清楚）：
- 三个客户端**全部进程内单例**，避免每请求重建 httpx 连接池；
- **显式**给了 `timeout=60` / `max_retries=1` / `max_tokens`（对话 1024、分析 1536）——
  注释里解释了为什么必须给：无 timeout 会让网关挂起时长占并发槽；默认 `max_retries=2` 配合 SSE
  会把一次用户请求放大成 3 次上游计费；无 max_tokens 则输出无界。
- **温度分层**：聊天要自然（0.7），抽取要确定（0）——这个分层是对的。

**缺失**：无模型降级/多网关容灾（`observability.py` 的 `LLMUsage.failover` 字段已预留但无人写入）；
无 Function Calling / Tool Calling 能力（网关是否支持未验证，见 §1.4）。

**结论**：✅ 完备。作为「大脑」的硬件基础已经到位，问题在于它没被赋予决策权。

### 1.2 记忆 —— ⚠️ 部分具备

**实现位置**：`ai/memory.py`（36 行）+ `models/chat.py`

**已具备：短期对话窗口**

```python
# ai/memory.py:26-35
msgs = await ai_crud.list_messages_tail(db, session_id, KEEP_RECENT)  # 只取最后 6 条，走索引
for m in reversed(msgs):
    used += len(m.content)
    if used > MAX_TOKENS or len(picked) >= KEEP_RECENT:
        break
```

- 窗口口径：`KEEP_RECENT_MESSAGES=6` 条 / `MAX_HISTORY_TOKENS=2000`；
- 从库里**只取尾部 N 条**（走 `idx_messages_session_ts` 索引），不是全量读进来再切片——这点做得对；
- 持久化：`sessions` / `messages` / `feedback` / `faq` 四张表，时间戳为 BIGINT 毫秒。

**缺失（4 项）**：

| 缺失能力 | 说明 | 影响 |
|---|---|---|
| **长期记忆** | 无用户画像 / 偏好 / 常用分类 / 历史决策的持久化 | 每轮对话从零开始，记不住「我习惯把打车记交通」 |
| **会话摘要压缩** | 超出窗口的早期消息**直接丢弃**，无 summary 滚动压缩 | 长对话必然「失忆」，且是断崖式的 |
| **工作记忆** | 工具中间结果 / 推理中间态无处存放 | （当前无工具，问题未暴露；一旦加工具立刻成瓶颈） |
| **跨会话记忆** | 每个 session 彼此隔离 | 换了会话，之前聊过的上下文全丢 |

**附带缺陷**：`memory.py:29-32` 是「先累加再判断」，**超预算的那条会被整条丢弃**。
若某条消息本身超过 2000 字，窗口会直接变空。更稳的做法是先 append 再判断，或对超长单条做截断。

**结论**：⚠️ 只有「短期滑动窗口」，属于最低配记忆。够撑一个 6 轮以内的问答，撑不起多轮任务。

### 1.3 规划 —— ❌ 缺失

**核查结果：全项目没有任何规划（Planning）模块。**

- `ai/` 目录下 12 个文件，无 `planner.py` / `plan.py` / `agent.py`；
- 全局 grep `AgentExecutor` / `create_react` / `langgraph` / `plan` 均无命中。

**当前所谓「流程」是什么**：

| 链路 | 本质 | 证据 |
|---|---|---|
| 对话 | 单次 LLM 调用，无步骤 | `routers/ai.py:291-292` |
| 分析/预算 | **固定两段式 pipeline**：先查库组包，再让 LLM 填文本字段 | `analyze_chain.py:85-137` |
| 记账 | **硬编码 9 步流水线** | `routers/ai.py:680-1059` |

以记账为例，那 9 步（校验 → 幂等 → 占位 → 解析 → 意图过滤 → 归一化 → 分支 → 入账 → 回写）
全部由 Python 的 `if/for` 写死。LLM 只被调用**一次**，负责「把这句话拆成结构化条目」，
不参与「先做什么、再做什么、失败了怎么办」的任何决策。

**缺失（4 项）**：任务分解（Decomposition）、多步计划（Plan）、子目标管理、动态重规划（Replan）。

**一个典型的「缺规划」症状**：用户说「帮我分析这几个月为什么超支，并给个下月预算」——
这是**一个需要 3~4 步的复合任务**（查多个月数据 → 定位异常月 → 归因 → 生成预算）。
当前系统只能把它当成一句普通聊天丢给 LLM，模型没有取数手段，只能泛泛而谈或拒答。

**结论**：❌ 完全缺失。这是当前系统离 Agent 最远的一块。

**这份文档从未被执行。** 它是「计划」，不是「现状」。

**当前用什么替代工具调用**：

| 替代方案 | 位置 | 局限 |
|---|---|---|
| 静态注入财务块 | `ai/context.py::build_finance_block` | **只有当月**：本月收支 + 上月总支出 + 当月 Top5 |
| 规则闸门 + FAQ 检索注入 | `ai/faq_retriever.py::build_knowledge_block` | 只覆盖 FAQ 表里那几条固定问答 |

**直接后果**（对应设计文档 §5.4 的题集）：

| 用户问题 | 当前能否回答 | 原因 |
|---|---|---|
| 本月花了多少 | ✅ | 财务块里有 |
| **上个月支出多少** | ❌ | 只有环比数，无绝对值 |
| **今年 3 月收入多少** | ❌ | 块里没有 3 月数据 |

| **最近三个月哪个月花最多** | ❌ | 无趋势数据 |
| **我买过打印纸吗** | ❌ | 无关键词检索能力 |

**结论**：❌ 缺失。这是**优先级最高**的缺口，也是从「Chatbot」迈向「Agent」的**分水岭**。
好消息是设计文档已经写到「可以直接抄代码」的程度，落地成本可控。

### 1.5 环境感知 —— ⚠️ 部分具备（静态感知）

**已具备**：

1. **财务环境**：`ai/context.py::build_finance_block`（`context.py:46-96`）
   - 查询：当月收支汇总 + 上月总支出（环比）+ 当月支出 Top5 分类（含占比）
   - 拼成自然语言块注入 system prompt
   - **降级设计值得表扬**（`context.py:59-70`）：DB 查询失败时**不返回空串**，
     而是返回「⚠️ 暂时查不到数据，禁止编造」的显式口径块。注释解释了为什么：
     该块同时承担「禁止编造数据」这条强约束，若在 except 里 `return ""`，
     约束会随空串一起消失，模型立刻恢复自由发挥并臆测数字。**降级必须是显式的。**

2. **知识环境**：`ai/faq_retriever.py::build_knowledge_block`（`faq_retriever.py:370-393`）
   - 规则闸门 `_needs_knowledge`：只有「疑问句 + 知识库主题词」且**不含数据向词汇**的短问句
     才发起检索，其余返回空串（**零 Embedding 成本**）
   - 闸门设计很细致（`faq_retriever.py:345-357`）：`_KB_QUESTION_HINT` 收「怎么/如何/为什么/支持/有哪些」，
     `_KB_EXCLUDE` 排「花了/买了/多少/趋势/统计/本月」——避免把「本月花了多少」误判为知识库问句白花一次 Embedding

**缺失**：

| 缺失能力 | 影响 |
|---|---|
| **跨月 / 趋势数据** | 上下文只有当月，任何历史问题都答不了 |
| **按需查询** | 感知是「每次全量注入」，不是「模型需要时去取」——既浪费 token 又不够用 |
| **场景感知** | 不知道用户当前在哪个页面、最近做了什么操作 |
| **数据新鲜度标记** | 模型无法区分「数据是刚查的」还是「缓存的」 |

**结论**：⚠️ 有感知，但是**静态快照式**感知（每次把固定几项数据塞进 prompt），
而非 Agent 应有的**按需主动感知**。这也正是「工具调用」缺失的连带后果。

### 1.6 控制循环 —— ⚠️ 仅雏形

**核查结果：后端没有 Agent Loop（ReAct 循环）。**

对话链路 `routers/ai.py:251-389` 的结构是：

```
校验 → 归属校验 → 配额/并发 → 组装 messages → 调一次 LLM → 落库 → 返回
```

**一次调用即结束，没有「观察结果 → 再决策」的第二轮。**

**已存在的「循环雏形」（2 处，但都不完整）**：

1. **记账的追问续写闭环**（`routers/ai.py:704-718`）—— 这是全项目最像「循环」的地方：

```python
if body.draft_id is not None:
    draft_log = await ai_crud.get_bookkeeping_log(db, body.draft_id)
    # 校验草稿归属 / status==0 / action=='clarify'
    combined = f"{draft_log.raw_text} {message}".strip()[:500]
    message = combined   # 把上一轮的原文与这一轮的回答拼起来重新解析
```

   流程：解析发现缺金额 → 返回 `clarify` + `draftId`（status=0 草稿）→ 用户补「35元」→
   带 `draftId` 重发 → 拼接原始文本重新解析 → 入账。
   **局限**：只覆盖「缺金额」一种情况；且需要前端配合保存并回传 `draftId`。

2. **前端的两段式意图路由**（`personal-ledger-uniapp/src/pages/ai-chat/index.vue:414-529`）：

```javascript
// ① 先走语义记账：created/clarify/duplicate 直接渲染
const handled = await tryBookkeeping(text, lastInputSource)
if (handled) { ...; return }
// ② 非记账消息（ignored: not_expense/query）→ 降级走流式对话
streamTask = sendChatStream(sessionId.value, text, {...})
```

   **这是当前唯一真正在运行的「决策 → 回退」控制逻辑，但它跑在客户端**。
   意图判定实际由后端的 `parse_bookkeeping` 完成（LLM 输出 `intent` 字段），
   前端根据 `action === 'ignored' && reason === 'not_expense'` 来决定降级——
   **相当于把编排逻辑拆成了「后端解析 + 前端分支」两半。**

**由此引出的功能不对称问题**：

| 端 | 是否有记账入口 | 证据 |
|---|---|---|
| H5（uniapp） | ✅ 有 | `ai-chat/index.vue` 调 `aiBookkeeping` |
| **Web（React）** | ❌ **没有** | `AiChat.jsx:197` 只调 `/chat/stream`，全文件无 `bookkeeping` 调用 |

也就是说，**同一套后端，Web 用户根本用不上自然语言记账**。这是编排逻辑放在前端的直接代价。

**缺失**：服务端 ReAct 循环、观察-行动-再观察、轮次上限、循环内超时与降级
（后三项在设计文档 M2 里已给出方案，未实现）。

**结论**：⚠️ 有「单次决策 + 回退」的雏形，没有「多轮感知-决策-行动」的闭环。

### 1.7 安全约束 —— ✅ 较完备（本项目最大亮点）

这一块做得**明显高于一般毕设水平**，且是唯一「超出 Agent 最低要求」的模块。

| 安全维度 | 实现位置 | 说明 |
|---|---|---|
| **数据脱敏** | `ai/security.py::desensitize` | 手机/银行卡/身份证/邮箱 → 占位符；顺序敏感（先长后短）+ 幂等（占位符不被二次替换） |
| **注入防护** | `ai/security.py::guard_injection` | 覆盖中英文的越权指令/角色劫持/输出劫持；命中即 `[FILTERED]`，「宁可误伤也不放行」 |
| **统一清洗入口** | `routers/ai.py::_safe_user_text` | 上云前脱敏 + 过滤；**落库保留原文**，只有上云那份被清洗；日志只记长度不记原文 |
| **行为边界** | `ai/chat_chain.py::SYSTEM_PROMPT` | 四段式：身份 / 行为边界 / 数据口径 / 不确定性处理；明确「严禁声称已帮您记录」 |
| **配额闸门** | `routers/ai.py::_quota_gate` | 原子 `consume_quota`（单语句校验+自增），免费/会员分档（10/100 次对话） |
| **并发限流** | `utils/ai_concurrency.py` | per-user 信号量；返回 **release 闭包**而非裸 Semaphore，规避升级导致的释放错位 |
| **语音防护** | `routers/ai.py:544-601` | 滑动窗口限流 + 扩展名白名单 + **魔数校验** + 分块读取防打爆内存 |
| **幂等** | `routers/ai.py:720-786` | 强幂等（`client_msg_id` + 唯一键）+ 弱幂等（`dedup_hash` + 300s）；**先写后查**解决并发 |
| **审计链** | `ai_bookkeeping_logs` | `parent_id` 串起「记账 → 修改 → 撤销」；`parse_json` 存 LLM 原始输出（天然评测样本） |
| **反幻觉** | 全链路 | `amount` 绝不猜测（宁可 None 触发追问）；数值字段服务端算；预算 `_sanitize_budget` 夹逼 |
| **可观测** | `ai/observability.py` | Token / TTFT / 延迟按 (kind, user_id) 聚合 |

**仍缺失**：

| 缺失项 | 影响 |
|---|---|
| **内容安全审核**（输入+输出双向） | 无涉政/涉黄/违法内容过滤，只有「记账相关性」的业务边界 |
| **输出侧数字校验** | 系统 prompt 要求「只引用注入数据」，但**没有代码层校验**模型是否真的没编数字 |
| **可观测落库** | Token 聚合是**进程内存态**，重启即清零、不跨实例（`observability.py` 注释已自认） |
| **多进程一致性** | `ai_concurrency` / `throttle` / `faq_retriever._index` 均为进程内存态，多 worker 下失效 |

**结论**：✅ 较完备。安全约束这块甚至可以反哺——一旦加入工具调用，
已有的「工具只读 + 闭包注入 user_id」设计（见设计文档 §4.3）可以直接复用同一套安全哲学。

## 2. 缺口清单：还需补充哪些模块

### 2.1 模块作用说明

| 优先级 | 模块 | 作用 | 为什么需要 | 落地成本 |
|---|---|---|---|---|
| **P0** | **工具调用层**<br>`ai/tools.py` + `ai/chat_flow.py` | 把只读查询包装成 LLM 可调用的工具，让模型自主决定「要不要查、查什么」 | **分水岭**。没有它，跨月/检索类问题永远答不出；有了它，加能力=加工具，不改路由 | 低（设计文档已给全码，~2.5 人日） |
| **P0** | **服务端统一编排入口**<br>意图路由下沉 | 把 uniapp 客户端的「先记账→失败降级对话」逻辑移到后端，Web/H5 共用一套 | 消除 Web 端「没有记账入口」的功能不对称；编排逻辑不应在客户端 | 中（需改两端调用） |
| **P1** | **会话摘要器**<br>`ai/summarizer.py` | 超出窗口的早期对话滚动压缩成摘要，而非直接丢弃 | 让长对话不再断崖式失忆 | 低 |
| **P1** | **长期记忆存储** | 持久化用户画像/偏好/常用分类/历史决策 | 让助手「认识」用户，而不是每轮从零开始 | 中（需建表 + 写入时机） |
| **P1** | **规划器（Planner）** | 把复合请求分解为多步子任务并编排执行顺序 | 支撑「分析+归因+预算」这类复合任务 | 中高（依赖工具层先落地） |
| **P1** | **反思/校验（Critic）** | 输出自检：数字是否来自工具结果、结论是否自相矛盾；失败则重试 | 补上「输出侧数字校验」这块安全缺口，显著降低编造率 | 中 |
| **P2** | **环境感知扩展** | 跨月/趋势上下文、按需查询、用户场景快照 | 提升回答的时效性与贴合度 | 低（工具层落地后自然获得大半） |
| **P2** | **可观测落库 + 评测集** | Token 落库、工具调用链追踪、导出评测数据集 | 支撑调优决策与论文实验；`parse_json` 已是天然样本 | 低 |
| **P2** | **内容安全审核** | 输入输出双向内容过滤 | 补上唯一的合规缺口 | 中（可能需外部服务） |

### 2.2 优先级建议（按「投入产出比」排序）

**第一梯队（P0，决定「算不算 Agent」）**

1. **工具调用层**——这是唯一一个「不落地就永远不是 Agent」的模块。
   建议严格按 `docs/工具调用对话实施指南.md` 执行：**先跑 M0 探针**验证 agnes 网关
   是否支持 function calling（该文档 §1 明确标注「未经验证」），
   支持则走 M1+M2，不支持则退到「静态注入扩展 6 个月块」的降级方案（改动仅 `context.py`）。
   > 关键设计约束（务必保留）：**工具只读**；`db`/`user_id` 走闭包注入，
   > **绝不出现在模型可见的参数 schema 里**（模型在结构上无法越权查他人数据）。

2. **服务端统一编排入口**——把前端的两段式路由下沉到后端。
   收益是双份的：Web 端补上记账能力 + 编排逻辑回到该在的地方。

**第二梯队（P1，决定「好不好用」）**

3. **会话摘要器 + 长期记忆**——两者一起做，才能让「记忆」从最低配升到可用。
4. **规划器 + 反思校验**——依赖工具层，工具落地后紧接着做，形成完整闭环。
   这两块做完，系统才真正具备「自主完成复合任务」的能力。

**第三梯队（P2，决定「稳不稳、可不可评」）**

5. **可观测落库 + 评测集**——成本低、对论文直接有用（`parse_json` 已是现成数据集）。
6. **内容安全审核**——合规兜底，按答辩/上线要求决定是否做。

## 3. 目标架构：补齐后的形态

```
用户输入（Web / H5 / 语音）
        │
   ┌────▼─────────────────────────────────────┐
   │ 编排层（新增）                             │
   │  意图路由 → 规划器 → 控制循环（ReAct）      │
   └────┬─────────────────────────────────────┘
        │
   ┌────▼─────────────────────────────────────┐
   │ 认知层                                     │
   │  LLM 大脑（已有） │ 记忆（升级） │ 反思校验（新增）│
   └────┬─────────────────────────────────────┘
        │
   ┌────▼─────────────────────────────────────┐
   │ 行动层                                     │
   │  查询工具（新增） │ 记账写入（已有）          │
   └────┬─────────────────────────────────────┘
        │
   ┌────▼─────────────────────────────────────┐
   │ 感知层                                     │
   │  财务上下文（已有） │ 知识库检索（已有） │ 环境快照（新增）│
   └────┬─────────────────────────────────────┘
        │
   ┌────▼─────────────────────────────────────┐
   │ 约束层（已有，直接复用）                     │
   │  安全脱敏 │ 配额限流 │ 审计幂等               │
   └──────────────────────────────────────────┘
```

**关键判断**：**约束层与认知层的大脑已经就绪，不需要重做**。
真正要补的是**编排层（全新）**、**行动层的一半（查询工具）**，以及**认知层的记忆升级**。
换句话说，这个项目距离 Agent 并不远——缺的是「编排骨架」，而不是「重写」。

## 5. 小结

| 维度 | 评价 |
|---|---|
| 工程完成度 | **高**。单例复用、超时护栏、幂等、审计、降级路径、契约注释，均超出一般毕设水平 |

**一句话**：这是一个**基础扎实、但骨架未长成**的系统。
它的「大脑」和「免疫系统」已经很强，只差「手脚（工具）」和「意图（规划）」——
而这两样，恰好都已经写好了设计文档。
