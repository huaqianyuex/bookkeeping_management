## 一、兑换码：从生成到体验资格的完整流程

### 1.1 一句话概览

**管理员批量生成兑换码 → 线下分发 → 普通用户核销 → 会员（体验）资格立即生效。**

兑换码是「免费体验会员」的唯一自助入口：不经过支付网关，管理员发码、用户核销即可获得会员资格。

### 1.2 数据模型

**`membership_codes`（兑换码表）**

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK | 主键 |
| `code` | VARCHAR(16) UNIQUE | 16 位兑换码，字符集 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`（**去除 0/O/1/I**，防用户手抄歧义） |
| `days` | INT | 该码可开通的会员天数 |
| `status` | TINYINT | **0=未使用　1=已使用　2=已作废** |
| `batch_no` | VARCHAR(32) | 批次号（默认生成时间戳），便于按批次管理 |
| `used_by` | BIGINT NULL | 核销用户 ID（FK → users.id，SET NULL） |
| `used_at` | DATETIME NULL | 核销时间（DB 时钟） |

唯一键 `uk_membership_codes_code` 是防串码的最后一道防线。

**`user_membership`（用户会员表）**

| 列 | 说明 |
|---|---|
| `user_id` | 唯一，每用户一行（免费用户可以没有行） |
| `tier` | 0=免费　1=会员 |
| `expires_at` | 到期时间；由 `DATE_ADD(NOW(), INTERVAL n DAY)` 写入（**DB 时钟**，避免应用/DB 钟差） |
| `source` | 开通来源：**0=兑换码**　1=管理员开通　2=充值购买 |

### 1.3 管理员生成兑换码

```
POST /api/admin/membership/codes          鉴权：get_current_admin（管理员专用）
Body: { "count": 10, "days": 30, "batchNo": "2026双十一" }   # batchNo 可选
```

处理链（`crud/membership.py::generate_codes`）：

1. **候选池生成**：一次凑够所需数量，池内自身去重；
2. **批量查库去重**：一条 `IN` 查询剔除库中已存在的码（**替代逐条 SELECT 的 N+1**，count=500 时 DB 往返从最多 500 次降到 1~2 次）；
3. **唯一键兜底**：极端并发下由 `uk_membership_codes_code` 拒绝，绝不静默串码；
4. **落库**：`status=0`、`batch_no` 默认生成时间戳。

响应返回**明文码列表**，便于管理员整批复制分发：

```json
{ "code": 200, "message": "已生成 10 张兑换码",
  "data": { "batchNo": "20261011183000",
            "codes": [ { "id": 1, "code": "A7KM2P9XQW4ZRT6B", "days": 30, "status": 0, ... } ] } }
```

配套管理端点：

| 端点 | 说明 |
|---|---|
| `GET /api/admin/membership/codes` | 兑换码分页列表（可按 `status` 筛选：0未使用/1已使用/2已作废） |
| `PUT /api/admin/membership/codes/{id}/void` | 作废（**仅 status=0 可作废**，取行锁防与核销并发冲突） |
| `POST /api/admin/membership/grant` | 不经兑换码，直接给指定用户开通/延期（source=1） |

### 1.4 普通用户核销兑换码

```
POST /api/membership/redeem              鉴权：get_current_user
Body: { "code": "mp-a7km-2p9x-qw4z-rt6b" }
```

处理链（`routers/membership.py::redeem` → `crud/membership.py::redeem_code`）：

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | **限流闸门** | `redeem_rate_limiter`：10 次 / 60 秒，超频 429。核销是带行锁的写操作，需防脚本高频空转打库 |
| 2 | **归一化** | 去空格/连字符、转大写 —— 兼容从聊天工具粘贴的 `MP-XXXX-XXXX-XXXX` 分组形态 |
| 3 | **行锁查码** | `SELECT ... FOR UPDATE`：同一码并发提交时只有一个事务能拿到锁 |
| 4 | **状态校验** | 不存在 / 已使用 / 已作废 → 400 + 中文原因 |
| 5 | **标记核销** | `status=1`、`used_by=user_id`、`used_at=DB NOW()` |
| 6 | **会员期叠加** | 一条 UPSERT 完成（见下） |
| 7 | **同事务提交** | 步骤 5+6 在同一事务，不留「码已用但会员未开」的半成品 |

**会员期叠加语义**（`_extend_membership_stmt`）：

```
无会员行  → INSERT tier=1, expires_at = NOW() + days
已有会员行 → expires_at = DATE_ADD( GREATEST(COALESCE(expires_at, NOW()), NOW()), INTERVAL days DAY )
```

即 **base = max(NOW, 现有到期时间)** —— 未到期时续费**不损失剩余天数**。
整段由 SQL 原子完成：若用「SELECT 读 → Python 算 → UPDATE 写回」，两个并发事务会读到同一旧值、后提交者覆盖前者，导致**码已核销但天数只加了一次**（真金白银的天数丢失）。

响应：

```json
{ "code": 200, "message": "兑换成功，会员已延长 30 天",
  "data": { "tier": 1, "expiresAt": "2026-11-10T18:30:00" } }
```

### 1.5 体验资格的生效与失效

**生效判定是「惰性」的**（`crud/membership.py::get_effective_membership`）：

```
tier == 1 且 expires_at > NOW()  →  会员生效
```

- 过期**不写库**，查询时判定即可 —— 省掉一个定时降级任务；
- 所有配额判断只走 `get_tier()` **单一入口**，不在别处自行比较 `expires_at`；
- 到期比较交给 DB 的 `NOW()`，避免多机时区/钟差导致会员提前或延后失效。

**用户侧可查的接口**：

| 端点 | 说明 |
|---|---|
| `GET /api/membership/status` | 等级 + 到期时间 + 今日用量 + 权益矩阵（会员中心数据源） |
| `GET /api/membership/redemptions` | **本次新增**：我的兑换记录（体验资格来源追溯），id 倒序分页；出参刻意不含 `usedBy` / `batchNo` 等管理侧字段 |

### 1.6 兑换码状态机

```
        ┌──────────────┐
        │  0 未使用     │ ← 生成时
        └──┬────────┬──┘
   核销    │        │  作废（管理员）
        ▼            ▼
  ┌──────────┐  ┌──────────┐
  │ 1 已使用  │  │ 2 已作废  │
  └──────────┘  └──────────┘
   （终态，不可逆）  （终态，不可逆）
```

## 二、角色权限范围

### 2.1 设计口径

**管理员的职责在管理后台，不需要也不应产生个人记账与对话数据。**

因此把权限边界落在**服务端依赖**上，而不是靠前端隐藏入口 —— 前端隐藏只是体验优化，
权限边界必须在服务端成立。三个角色依赖的分工：

| 依赖 | 语义 | 使用场景 |
|---|---|---|
| `get_current_user` | 只校验登录态，**任何角色都通过** | 账号自身功能（个人资料、会员、充值） |
| `get_current_regular_user` | 登录态 + **拒绝管理员（403）** | 用户侧业务端点（记账 / 对话） |
| `get_current_admin` | 登录态 + **必须是管理员** | 管理后台 |

`get_current_regular_user` 与 `get_current_admin` **互补且互斥**：
role=1 走管理后台、role=0 走用户业务，不存在两边都能进的端点。

### 2.2 功能范围矩阵

| 功能域 | 端点前缀 | 普通用户 role=0 | 管理员 role=1 |
|---|---|---|---|
| 记账（账单 / 分类 / 统计） | `/api/records` `/api/categories` `/api/statistics` | ✅ 可用 | ❌ **403** |
| AI 对话与分析 | `/api/ai/**`（除下方两处） | ✅ 可用 | ❌ **403** |
| AI 管理统计 / FAQ 重建 | `/api/ai/admin/stats` `/api/ai/faq/rebuild` | ❌ 403 | ✅ 可用 |
| 会员 / 充值 | `/api/membership/**` `/api/recharge/**` | ✅ 可用 | ✅ 可用 |
| 个人资料 / 改密 | `/api/user/**` | ✅ 可用 | ✅ 可用 |
| 管理后台 | `/api/admin/**` | ❌ 403 | ✅ 可用 |

管理员调用用户侧业务端点的返回：

```json
HTTP 403
{ "code": 403, "message": "管理员账号无需使用该功能，请前往管理后台", "data": null }
```

| 文件 | 说明 |
|---|---|
| `utils/auth.py` | 模块 docstring 含**权限矩阵**；新增 `get_current_regular_user` |
| `routers/record.py` | 5 个端点改挂 `get_current_regular_user` |
| `routers/category.py` | 4 个端点 |
