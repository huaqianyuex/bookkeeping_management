## 二、当前 AI 实现说明

AI 能力按场景拆成四条链，整体为“LangChain + OpenAI 兼容网关（Agnes）+ 进程内内存态护栏”的架构：

1. **对话链**：进程内单例 `ChatOpenAI`，`/chat` 非流式 + `/chat/stream` SSE；system prompt = 基础约束 + 实时财务数据块 + FAQ 知识库块，两块均为“有则注入、无则跳过”。
2. **记账链**：温度 0 的分析模型 + `with_structured_output(method="function_calling")` 抽取意图/条目；`normalizers.py` 做金额/日期规则兜底，`category_alias.py` 做分类映射（已修复“今日用餐”被中间子串误判成“日用”的问题）。
3. **分析链**：消费分析/预算规划；数值字段由系统计算，LLM 只写文案；`_sanitize_budget` 对预算做三道夹逼校验（收入上限、分类限额归一、超和缩放）。
4. **FAQ 检索**：进程内内存向量索引 + 原始余弦过滤（已修复归一化阈值失效 bug）、关键词降级、重建 single-flight + 60s 冷却、query 向量 LRU 缓存。

配套护栏：会员配额原子闸门（`consume_quota` 单语句条件自增）、进程内 per-user 并发信号量、STT provider 注册表、脱敏 + 提示词注入过滤管道、LLM 调用可观测聚合（含 TTFT 首字延迟）。

**整体评价**：这是“毕设偏工程化”的水准。代码注释大量记录了历史 bug 的修复理由（幂等键死日志释放、DB 时钟 vs 应用时钟口径、Embedding 维度校验、死锁根因等），兜底意识很强。主要问题集中在成本计量、安全清洗覆盖面和护栏口径一致性上。

## 四、改进方案（按优先级）

### P0 —— 先堵成本与安全

1. 给 `analyze_expense` / `plan_budget` 补齐 `Timer + record_call`，与 chat/bookkeeping 链对齐。
2. `amend` 复用 `_quota_gate(db, user_id, "bookkeeping")` 并纳入 `try_acquire` 并发槽；同时补记 `AiBookkeepingLog.message_id`。
3. 将脱敏上移到统一组包层：`analyze` 的 query 先 `_safe_user_text`；`faq_retriever._embed_query` 入参先 `desensitize`（占位符不影响相似度）。
4. 给 `/faq/search` 挂独立滑动窗口限流（复用 `SlidingWindowRateLimiter`），或并入每日配额。

### P1 —— 可靠性与成本可见性

5. token 计量补齐：流式对话取末尾 chunk 的 `usage_metadata`；结构化输出改用 `invoke + 手动 Pydantic 校验`（失败降级宽松解析一次），拿回真实 usage。
6. `llm.py` 增加网关级 failover / 熔断：配置 `BACKUP_BASE_URL` / `BACKUP_API_KEY`，主网关连接错误/5xx/超时切备用并置 `failover=True`；对上游 429/5xx 用指数退避重试。
7. STT：provider 复用连接池（成员级 `httpx.AsyncClient`）；失败不占限流槽；服务端补时长/采样率校验。
8. `build_user_context` 用 `asyncio.gather` 并行 3 条查询；tier 在请求内复用；财务块按 `(user_id, 月份)` 短 TTL 缓存（记账后失效）。

### P2 —— 结构与扩展性

9. 拆分 `routers/ai.py` 为 `sessions / chat / analyze / faq / voice / bookkeeping`，抽出公共 `router_utils.py`（`_safe_user_text`、分类加载、parent 查找、配额/并发获取）。
10. 清理 `schemas/ai.py` 注释死代码，补 `ChatOut.message_id` 契约，统一 AI 失败结构 `{error, code}`。
11. 建 `ai/prompts.py` 集中管理 prompt 与模型参数；输出约束用 `field_validator` / 后校验兜底，非法时二次纠正或明确降级。
12. `memory.py` 引入轻量 tokenizer 或“字符数 × 系数 + system prompt 长度”整包预算。
13. `_slots` / `_agg` 加惰性清理或容量上限；多 worker 部署方案（Redis）写入 README。
14. 补测试盲区：amend 无配额、analyze query 脱敏、FAQ search 限流、token 落库，各加 1-2 条断言。

## 五、推荐落地步骤

1. 先做 P0-1/2/3/4：改动小、相互独立，每项补一个测试（`test_analyze_chain.py` 已有 fake LLM 套路可复用，`test_ai_endpoints.py` 已有配额/SSE 测试基建）。
2. 再做 P1-5/6（计量 + failover）：纯增量，`.env` 增加 `BACKUP_BASE_URL` 等新配置，不破坏现有契约。
3. 再做 P1-7/8（STT、并行化）。
4. 最后做 P2 大重构。拆分 `routers/ai.py` 时保持路由 path、裸 JSON、camelCase / snake_case 契约一字不动，靠现有 `test_ai_endpoints.py` 守回归。
5. 全程跑 `pytest` 回归；注意 `.pytest_cache` 目录权限问题（当前环境该目录不可写）。

## 六、风险与注意事项

- **前端契约是硬约束**：AI 模块全裸 JSON、时间戳毫秒、`data` 内 snake_case 等，整改不能动；所有改动保持服务端内部即可。
- **配额“失败不回滚”是既定取舍**（防刷量优先）：给 amend 加配额时需确认失败回滚口径与现状一致。
- **脱敏是启发式**：正则仅覆盖大陆手机号/卡号/证件/邮箱，姓名、地址等仍会外传；生产环境应升级为可配置规则并接入模型供应商 DPA。
- **`with_structured_output` 换用法的兼容风险**：部分兼容端点不支持严格 json_schema，改 `invoke + 手动校验` 时保留 function_calling 分支。
- **单 worker 是当前部署前提**：任何“无限成本口”的评估都以单 worker 为准；上多 worker 前，配额/并发/限流/观测需一起迁 Redis / 落库，否则全部失真。
- 本报告为纯审查结论，未改动任何代码。
