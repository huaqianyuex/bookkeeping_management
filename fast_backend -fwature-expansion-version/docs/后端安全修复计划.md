# 后端安全整改路线图（fast_backend）

> 版本：v2.0（规划稿）  
> 日期：2026-09-24  
> 核验基线：当前工作区快照；当前仓库存在大量未提交修改，本计划不代表干净提交基线。  
> 对应报告：`docs/后端安全分析报告.md`  
> 文件级实施方案：`docs/后端安全修复文件级实施方案.md`  
> 目标：将 18 项发现按风险、根因和依赖关系转化为可验证、可回滚的整改计划。

---

## 0. 结论与实施门槛

### 0.1 结论

1. **P0 必须先封堵账户接管、AI 费用滥用和生产配置失效。** 未完成 P0 前，不应将服务暴露到公网或恢复多 worker 部署。
2. **不继续沿用 v1 的两个不安全假设**：固定可预测的 JWT 开发密钥、MySQL advisory lock 包裹多次 `commit` 的普通 `AsyncSession`。
3. **H1 不能只改后端正则。** 6 位 PIN 同时存在于 Web、uniapp、API 文档和后端 Schema，必须做前后端契约迁移。
4. **M5 建议从“中危”降为低危模型鲁棒性问题。** 当前 LLM 无工具、无跨用户数据、无资金授权；若未来接入工具或自动操作，应立即升为 P1/P0。
5. **工程门禁是整改的一部分。** 当前无标准 pytest 测试、无锁依赖、无迁移框架，不能把一次性脚本或真实 LLM 压测作为验收证据。

### 0.2 因约束信息为空，本稿采用的临时假设

| 假设 | 临时处理 | 实施前必须确认 |
|---|---|---|
| 部署形态 | P0 期间固定单 worker、单实例 | 实际 worker 数、是否多副本、是否有可信反向代理 |
| 用户规模 | 小型毕设/内部系统 | 是否公网、用户数、峰值并发、是否存在 NAT 共享出口 |
| 基础设施 | 暂不假设已有 Redis | 是否允许新增 Redis；不能新增时采用 MySQL 原子限流或明确限制单 worker |
| 数据库 | MySQL，允许先备份后做加列/加索引 | 是否允许维护窗口、是否有测试库、是否已有 Alembic |
| 密码产品契约 | 新注册采用强口令，存量 6 位 PIN 登录后强制迁移 | 是否必须永久保留 PIN；前端能否同步升级 |
| AI 供应商 | 允许设置供应商账户硬预算 | 实际供应商、单价、月预算、最大可接受响应长度 |
| 团队与时间 | 1 名全栈开发、QA/安全兼职、1–2 周完成 P0/P1 | 实际人数、截止日期、是否允许维护窗口 |

### 0.3 立即止损措施

在完整代码改造前，由运维和后端负责人共同确认：

- 暂停公网访问，固定 `--workers 1`，禁止当前内存限流被误认为多实例安全控制。
- 禁止生产启用 `JWT_SECRET_INSECURE_OK`；生产必须有显式高熵 `JWT_SECRET`。
- 将 AI 端点置于维护开关或供应商账户硬预算下，先限制调用频率、并发和输出长度。
- 关闭生产 SQL `echo`，确认日志采集不包含 SQL 参数、金额、手机号、用户名和聊天内容。
- 备份数据库和配置；本轮不读取、不展示、不修改 `.env` 中的密钥值。
- 实施前先将当前未提交改动形成可追溯基线；不执行强制覆盖式 Git 操作，不自动提交。

### 1.1 P0 出口标准

以下条件全部满足才可结束 P0：

- 固定目标用户名在多个可信 IP 来源下仍受账号维度限流；并发请求不能绕过检查。
- 新注册不再接受 6 位纯数字；存量 PIN 有明确迁移路径。
- AI 成本端点全部有用户配额、并发上限、输出上限和供应商硬预算。
- 生产缺少 JWT/数据库配置时启动失败；生产 SQL `echo=False`。
- 限流、配额、JWT 和 AI 行为有自动化测试，测试不调用真实 LLM。
- P0 验证失败时，服务保持在维护状态或使用明确的安全降级策略，不恢复旧安全行为。

## 2. 根因分析

### 2.1 18 项发现的根因登记

| 编号 | 当前机制与证据 | 根因判断 | 计划中的修正 |
|---|---|---|---|
| H1 | `schemas/users.py:11-13` 将密码限制为 6 位数字；`routers/user.py:42-70` 以 `IP|用户名` 计数 | 密码空间过小，且没有账号维度的跨 IP 总量控制 | 密码策略迁移 + 规范化账号桶 + 可信 IP 桶 + 原子失败计数 |
| H2 | `routers/ai.py:166-332`、`:404-901` 调用 LLM/Embedding；`utils/throttle.py` 未被 AI 路由使用 | 外部付费资源没有成本、并发和供应商预算模型 | 统一 AI Guard，按端点权重限流、限 token、限并发，增加 kill switch |
| M1 | `crud/user.py:93-109` 改密只换哈希；没有 token version、refresh 或 logout 吊销 | JWT 生命周期只有“签名+过期”，没有版本/会话管理 | `token_version` 先实现全员失效；后续增加按设备 token |
| M2 | `config/settings.py:33-37` 先绑定 `JWT_SECRET`；`:64-92` 只修改 `os.environ` | 配置对象与环境变量有两个事实源，逃生分支没有更新实际签名密钥 | 生产 fail-closed；开发临时密钥随机生成且仅限开发 |
| M3 | `config/db_config.py:15-22` 缺 `DATABASE_URL` 时回退到源码弱连接串 | 配置缺失时 fail-open，弱凭据随源码分发 | 缺失即启动失败；开发 profile 显式允许，不允许生产继承 |
| M4 | `config/db_config.py:24-30` 固定 `echo=True` | 调试配置与生产配置未分离，SQL 参数进入日志面 | 生产 `echo=False`、参数脱敏、readiness 检查 |
| M5 | `routers/ai.py:180-194`、`:221-247` 回注数据库历史；`ai/memory.py:10-23` 原样恢复角色 | 历史消息与系统指令没有信任边界；但当前没有工具权限 | 标签/系统约束作为纵深防御，禁止 LLM 直接决定授权或资金操作 |
| M6 | `routers/ai.py:446-481` 先查 `dedup_hash` 再写；数据库仅对非空 `client_msg_id` 唯一 | 正确性依赖应用层预检，且占位没有失败恢复状态机 | 非 dry-run 强制 `clientMsgId`；同 key 持久化请求哈希和状态；数据库唯一约束仲裁 |
| M7 | `routers/ai.py:66-161`、`:77-101` 创建/列出/读取消息缺少完整资源预算 | 会话、消息、反馈只有局部字段限制，没有生命周期和分页契约 | 活跃会话原子配额、游标分页、消息上限、保留和清理任务 |
| L1 | `utils/security.py:17-20` 固定 bcrypt `rounds=10` | 哈希成本不可配置，也没有登录成功后的渐进 rehash | 基准测试后默认 12；识别旧 hash 并透明升级；长期评估 Argon2id |
| L2 | `routers/user.py:29-39` 显式返回“用户名已存在”；未知用户登录跳过 bcrypt | 业务错误直接成为用户名 oracle，且时序不同 | 统一外部错误契约、dummy hash、可选邮箱/短信激活；保留限流 |
| L3 | 注册无专门限流，先查用户名再插入 | 资源滥用和 check-then-create 竞态没有统一策略 | 以唯一键为最终裁决，注册按可信 IP/规范化用户名限流 |
| L4 | `routers/admin.py:93-105` 更新状态时丢弃操作者 ID；删除路径才有管理员保护 | 业务不变量没有下沉到共享领域逻辑 | 禁止自禁用；按产品规则保护管理员，并保证至少一个启用管理员 |
| L5 | `utils/upload.py:21-57` 只检查 Content-Type/后缀/大小；`main.py:32-34` 公开静态目录 | 信任客户端元数据，未以实际解码结果作为文件类型来源 | magic bytes + 完整解码 + 像素限制 + 重编码 + `nosniff` |
| L6 | `schemas/record.py:30-41` 无范围；`crud/record.py` 直接写 `type` | Record 与 Category 重复存储类型，多入口没有统一领域不变量 | 从分类推导类型；Schema、领域服务、DB CHECK 三层约束 |
| L7 | 实际 FAQ Schema 位于 `schemas/admin.py:37-41`，字段无 `max_length` | 输入、存储、重建成本和索引状态均无边界 | 创建/更新 Schema 分离、长度和非空校验、列表分页 |
| L8 | `schemas/admin.py:21-23` 的 `ids` 无 `max_length` | 文档建议不是运行时约束，批量 SQL/请求体无预算 | 最大 50、正整数 ID、请求体大小限制；大规模改异步任务 |
| L9 | `utils/throttle.py:47-92` 为进程内字典和线程锁；未配置可信代理 | 状态不跨 worker，请求级检查不是原子操作，IP 信任边界未定义 | P0 固定单 worker；生产多实例用 Redis 原子限流并显式故障策略 |

### 2.2 对原报告的校正

以下结论不能直接照搬原报告：

- M1 的“禁用/删除后旧 token 仍可用”不成立：当前 `utils/auth.py:30-37` 每次鉴权回查用户存在和状态；真正缺口是改密和没有 logout 吊销。
- M7 的“`size` 可拉全表”表述过重：`crud/ai.py:71-72` 已将 size 静默限制到 100；真正问题是 page 大 OFFSET、聚合成本，以及 `GET /sessions/{id}/messages` 无分页。
- H2 的“所有输出全量落库”不准确：chat/stream 助手消息落库，分析结果不一定落库；但仍缺 token、请求和费用预算。
- M6 之外还存在占位日志失败后长期“处理中”的恢复问题。
- L8 实际可由 `schemas/admin.py:21-23` 直接确认，应从 unconfirmed 改为 verified。
- L6 不只是越界值问题，还包括 `Record.type` 与 `Category.type` 不一致。
- M5 只有在未来引入工具、跨用户知识或自动资金操作时才会显著升级。

## 3. 可选方案与推荐取舍

成本单位为人日，包含设计、代码、测试和评审；不包含外部验证码、短信、云 Redis 的采购费用。

### 3.1 H1：密码与登录

| 方案 | 优点 | 缺点 | 成本 | 风险 | 结论 |
|---|---|---|---:|---|---|
| A. 分阶段强口令：存量先限流，下一次登录强制改密；新注册 12–128 位（高敏场景建议 15+），不强制无意义符号组合 | 从根上扩大密码空间；兼容迁移 | 前后端和用户习惯需调整；存量过渡期仍需限流 | 4–7 人日 | 用户锁定、客户端契约不一致 | **推荐** |
| B. 永久保留 6 位 PIN，仅做双维限流、验证码、指数退避 | 改动小，产品体验稳定 | 10^6 密码空间仍在；代理池、撞库、凭证填充风险只能缓解 | 3–5 人日 | 账号锁定 DoS；残余风险高 | 仅内部系统临时方案 |
| C. 密码less/短信或邮箱 OTP | 不依赖用户记忆密码 | 引入供应商、费用、送达失败和账号恢复流程 | 8–12 人日 | 外部服务故障、短信滥用 | 长期方案 |

推荐 A，并同时实施：用户名规范化、账号维度限流、可信 IP 维度限流、失败风险升级和统一错误响应。验证码不是密码强度的替代品。

### 3.2 L9：限流存储与并发原子性

| 方案 | 优点 | 缺点 | 成本 | 风险 | 结论 |
|---|---|---|---:|---|---|
| A. Redis Lua/原子计数 + TTL | 多 worker/多实例一致；可实现原子预留名额 | 新增基础设施和故障策略 | 3–5 人日 | Redis 不可用时需明确 fail-closed 或降级 | **生产推荐** |
| B. MySQL 行锁/唯一键计数 | 不新增中间件；跨进程一致 | 数据库写放大、热点锁、清理复杂 | 3–4 人日 | DB 压力和锁等待 | 无 Redis 时的中期方案 |
| C. 单 worker 内存字典 | 最快、零基础设施 | 重启清零；并发请求级检查不原子；不能水平扩展 | 1–2 人日 | 误认为已解决 L9 | **仅 P0 止损** |

推荐：P0 明确固定单 worker 并加启动检查；生产多实例前切 Redis。登录限流应在 bcrypt 前原子“预留失败名额”，避免多个并发请求同时通过 `is_locked()`。

### 3.3 H2/M7：AI 成本、并发和存储

| 方案 | 优点 | 缺点 | 成本 | 风险 | 结论 |
|---|---|---|---:|---|---|
| A. 单进程 Guard：用户日配额、分钟速率、并发信号量、端点权重 | 快速封堵；不改外部接口 | 重启清零；多 worker 可绕过 | 2–3 人日 | 阈值误伤；无法全局控费 | **P0 临时方案** |
| B. Redis 配额/租约 + 供应商硬预算 + usage ledger | 跨实例一致；可按 token/端点计费 | 需记录 usage、处理 Redis 故障和成本估算 | 4–6 人日 | 估算价格不准；账务复杂度上升 | **生产推荐** |
| C. 任务队列 + 异步 job | 可排队、取消、重试、限 provider 并发 | 交互式聊天体验改变；需要 job 状态和前端改造 | 8–12 人日 | 用户等待、任务堆积 | 长期/高并发方案 |

推荐分层实施：

- P0：进程内 Guard 封住成本，配额通过环境配置；`/faq/rebuild` 单独单例和冷却。
- 中期：Redis 原子配额、每用户并发 2、全局并发按压测确定，LLM 供应商设置月度硬限额和告警。
- 长期：分析/重建改异步队列，记录模型、输入/输出 token、估算费用、request ID 和状态。

建议初始值仅作压测起点：普通 chat 100 次/日、每用户并发 2；分析/bookkeeping 按 2 倍权重计；`/faq/rebuild` 仅管理员、每用户每日 1 次且全局同一时间只允许 1 个。最终数值必须由预算和峰值流量决定。

### 3.4 M1：JWT 撤销与会话

| 方案 | 优点 | 缺点 | 成本 | 风险 | 结论 |
|---|---|---|---:|---|---|
| A. `users.token_version` | 当前鉴权已经回查用户；无需每请求新增 token 查询；改密可全员失效 | 只能按用户版本失效，不能精确登出某设备；需要 DDL | 2–3 人日 | 旧 token claim 迁移；版本 bump 时全员掉线 | **最小可上线方案** |
| B. 启用 `user_token` 表，按 JTI 登记/撤销 | 支持设备级登出、审计和黑名单 | 迁移、清理、缓存和每请求校验复杂 | 3–5 人日 | 原始 token 存储风险；数据库依赖增加 | 中长期方案 |
| C. 短 access token + rotating refresh token | 泄露 access token 窗口短；刷新可撤销 | 前端需新增 refresh 流程；实现和迁移最大 | 6–10 人日 | refresh token 泄露、并发刷新竞态 | 长期方案 |

推荐 A 先落地；`token_version` 变更触发条件为改密、管理员禁用/角色变更和全员登出。若密钥疑似泄露，不做旧 token 宽限，直接轮换密钥并强制全员重新登录。

### 3.5 M6：AI 记账幂等

| 方案 | 优点 | 缺点 | 成本 | 风险 | 结论 |
|---|---|---|---:|---|---|
| A. 非 dry-run 强制 `clientMsgId`，数据库唯一键 + 请求哈希/状态机 | 客户端重试可安全复用；不会把相同消费永久禁止 | 需同步 Web/uniapp；旧客户端需兼容期 | 4–6 人日 | 客户端生成 ID 错误；pending 恢复逻辑复杂 | **推荐** |
| B. 独立短 TTL dedup reservation 表，唯一键仲裁 | 可保留无 ID 客户端的弱去重 | 需要清理、时间桶和状态迁移 | 3–5 人日 | 时间桶误伤/漏判；仍有短时重复风险 | 兼容方案 |
| C. MySQL `GET_LOCK` | 改动表面较小 | 连接级锁、多次 commit、锁名长度和连接池阻塞问题明显 | 2–3 人日 | 锁泄漏、连接池耗尽、误放行 | **不采用当前 v1 写法** |

强幂等键唯一约束应继续使用 `(user_id, client_msg_id)`。不要对金额、分类或 `dedup_hash` 做永久唯一约束，否则会阻止用户合法地购买两杯相同价格的咖啡。

## 4. 目标设计

### 4.1 认证与限流

1. 所有账号输入先做统一规范化，限流键使用规范化后的账号标识，不直接使用原始大小写/空格变体。
2. 只信任明确配置的反向代理；不能直接信任任意客户端提交的 `X-Forwarded-For`。
3. 登录/注册使用双维桶：
   - 账号桶：阻止换 IP 针对同一账号爆破；
   - IP 桶：阻止单 IP 喷洒大量账号；
   - 风险升级桶：高风险时要求验证码或指数退避。
4. 失败计数必须在 bcrypt/数据库操作前原子预留，避免多个并发请求同时通过检查。
5. 429 返回 `Retry-After`；401/400 外部文案不能泄露账号是否存在。

### 4.2 AI Guard

1. 所有可能调用 LLM/Embedding 的端点统一接入 Guard：chat、stream、两个 analyze、bookkeeping、带 message 的 bookkeeping PATCH、FAQ search、FAQ rebuild。
2. 会话创建、消息读取、反馈、批删另设低成本存储配额，不能把所有端点简单等同为 LLM 调用。
3. 每个端点配置：请求速率、日配额、并发、`max_tokens`、输入长度、输出存储上限。
4. SSE 在正常结束、异常、客户端断开和取消时都释放并发租约。
5. FAQ rebuild 只能管理员执行，并有全局单例、冷却和费用记录。
6. 增加 provider 账户硬预算、告警和全局熔断；应用层配额是主控制，供应商预算是最后防线。

### 4.3 JWT 生命周期

1. JWT 至少强制 `exp`、`sub`，规范 Bearer 解析；非法 `sub` 返回 401，不返回 500。
2. 增加 `token_version` 或 JTI 吊销机制，改密后旧 token 立即失效。
3. 令牌载荷加入 `iat`、`iss`、`aud`、`jti`，避免长期 token 无限使用。
4. 密钥轮换采用“新 key 签发、旧 key 验证”的受控过渡；若旧 key 泄露，不接受宽限。
5. 当前用户状态回查保留，作为禁用/删除的即时控制。

### 4.4 记账幂等与资源生命周期

1. 外部 LLM 调用不放在长数据库事务中；先原子预留幂等记录，再调用模型，最后用短事务写入 records 和成功结果。
2. 幂等记录至少包含：`user_id`、`client_msg_id`、`request_hash`、`status`、`record_ids`、`lease_expires_at`。
3. 相同 key+相同 hash：处理中返回可重试状态，已完成返回原结果；相同 key+不同 hash 返回冲突。
4. 会话列表和消息列表使用游标/有界分页；删除和保留策略有明确 TTL。
5. 任何 LLM 失败、进程崩溃或事务回滚都不能留下永久“处理中”记录。

## 8. 风险与回滚方案

### 8.1 通用发布原则

- 先在隔离数据库和 mock AI 环境验证，再进入预发布，最后生产灰度。
- 数据库变更先备份、先加列/索引，再发布代码；不以 `CREATE TABLE IF NOT EXISTS` 代替版本迁移。
- 保留功能开关：密码策略、强制 `clientMsgId`、AI 配额/熔断、Redis 限流后端。
- 代码回滚使用已评审的版本化提交或 `git revert`；不使用会覆盖未提交改动的 `git checkout`。
- 数据库回滚优先采用“旧代码兼容新 schema”的前向修复；不要在故障时立即删除新列或新索引。
- `.env`、密钥、token、证书和生产部署配置属于受控变更；必须由项目负责人明确批准后执行。

### 8.2 风险矩阵

| 风险 | 触发条件 | 影响 | 缓解 | 回滚/应急 |
|---|---|---|---|---|
| 密码策略导致用户无法登录 | 旧 PIN 用户无升级页面或客户端不支持 | 用户锁定、支持成本上升 | 预发布双版本；新注册先切；存量按风险分批 | 临时保持兼容读取，但不得关闭账号限流；修复客户端后继续强制迁移 |
| 限流误伤 NAT 用户 | 共享出口大量正常登录 | 可用性下降 | IP 阈值宽于账号阈值；监控 429 比例；仅允许经过审批的临时白名单 | 临时调高 IP 阈值或切换故障策略，不删除账号桶 |
| Redis 故障 | Redis 网络/服务异常 | 限流、配额不可用 | 生产敏感端点 fail-closed；健康检查和告警；本地仅作短时应急 | 按预案启用经过审计的 MySQL 方案或进入维护模式，禁止无提示退回无限流 |
| AI 配额误伤 | 阈值低于真实峰值 | 用户无法使用 AI | 权重化而非统一次数；灰度调参；按端点观察 | 临时提高配额或关闭非核心端点，保留 provider 硬预算 |
| JWT 全员失效 | 轮换密钥或 bump 版本 | 所有用户掉线 | 维护窗口、发布双版本、提前通知 | 若非泄露可回滚代码；若泄露不得恢复旧 key，执行重新登录和密钥轮换 |
| 强制幂等导致旧客户端失败 | 旧客户端不发送 `clientMsgId` | AI 记账不可用 | 兼容期双写、服务端生成短期兼容 ID、明确客户端版本 | 暂时关闭强制校验但保留唯一键和告警；不能恢复无约束重复写入 |
| advisory lock 锁泄漏 | 使用普通 `AsyncSession` 跨 commit 持锁 | 连接池耗尽、请求阻塞 | 不采用该实现；若必须使用则专用固定连接并检查返回值 | 立即摘除异常 worker，终止连接释放 named lock |
| SQL 日志泄露 | 调试开关误开 | PII 暴露、性能下降 | profile 分离、启动检查、日志扫描 | 关闭 echo/参数日志并清理受控日志；不能把旧日志继续当作安全 |
| 上传验证误拒合法图片 | 图片编码、EXIF、尺寸异常 | 用户体验下降 | 先收集真实样本，完整解码并限制异常而非仅看后缀 | 回滚到“拒绝未知类型”的安全降级，不恢复完全信任元数据 |
| 依赖升级破坏运行 | 宽松 `>=` 自动解析新版本 | 启动/接口回归 | 锁文件、干净环境安装、导入 smoke test | 回滚锁文件和应用版本，按 SCA 结果重新评估 |
| 数据清洗误删 | 统计口径不清直接删除冲突数据 | 财务数据损失 | 先导出、备份、对账、双人复核 | 从备份恢复并修正领域规则；不自动删除财务记录 |

### 8.3 数据库迁移顺序

1. 备份并记录当前 schema/数据量。
2. 在测试库执行迁移，验证空库和上一版本。
3. 先上线兼容字段和索引，再上线读取/写入逻辑。
4. 观察错误率、慢查询、锁等待和业务对账。
5. 稳定后再清理旧路径；旧路径清理单独审批，不与安全上线同一批次。
