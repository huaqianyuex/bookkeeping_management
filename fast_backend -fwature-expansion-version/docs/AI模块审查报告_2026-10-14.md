## 二、模块概览与调用链

架构：`FastAPI + SQLAlchemy 2.0 (asyncio) + MySQL + LangChain（ChatOpenAI / OpenAIEmbeddings）+ OpenAI 兼容网关（Agnes AI）`，四条独立链 + 进程内护栏。

```
┌─ 路由层 routers/ai.py（1565 行，17 个端点，裸 JSON 契约）
│   ├─ /chat /chat/stream        → ai/chat_chain.py（SSE/非流式 + 指数退避重试）
│   │                              ├─ ai/context.py        （实时财务数据块，3 条聚合 SQL）
│   │                              ├─ ai/faq_retriever.py  （知识库块，向量/关键词双模式）
│   │                              └─ ai/memory.py         （历史窗口：尾部 N 条 + 字符预算）
│   ├─ /analyze/expenses /analyze/budget → ai/analyze_chain.py（结构化输出 + 数值夹逼）
│   ├─ /bookkeeping（+amend/delete）     → ai/bookkeeping_chain.py（function_calling 抽取）
│   │                              ├─ ai/normalizers.py / ai/category_alias.py（规则兜底）
│   │                              └─ ai_bookkeeping_logs（幂等 / 草稿 / 审计）
│   ├─ /faq/search /faq/rebuild  → ai/faq_retriever.py（内存向量索引，admin-only 重建）
│   └─ /voice/*                  → ai/stt.py（Provider 注册表，Whisper 兼容）
├─ 支撑：ai/llm.py（单例客户端） ai/retry.py（退避） ai/security.py（脱敏+注入过滤）
│        ai/observability.py（token/TTFT） utils/ai_concurrency.py（信号量）
└─ 数据：crud/ai.py + models/chat.py + models/bookkeeping.py + ai_usage_daily（配额）
```

关键数据流（`/chat/stream`）：鉴权（regular_user）→ 会话归属校验 → tier 查询 → 并发槽 → 配额原子自增 → 落库用户消息 → 组包（历史窗口 + 财务数据块 + 知识库块）→ LLM 流式 → 落库助手消息 → `done` 事件。

注意：配额 / 并发 / 限流 / FAQ 索引 / 用量聚合全部为进程内存态，部署前提是单 worker（代码多处已显式声明）。

### 已确认的正面项

- 鉴权：AI 端点统一挂 `get_current_regular_user` / `get_current_admin` 双依赖矩阵，管理员与普通用户互斥。
- 越权：会话、消息、记录、反馈全部有归属过滤；FAQ 重建与全站统计仅管理员可调。
- 配额：`consume_quota` 单语句条件自增，无并发放大的 check-then-incr 窗口。
- 记账幂等：client_msg_id 唯一键 + 5 分钟 dedup + force 覆盖，死日志可释放幂等键。
- 语音：STT 限流先占后还（失败 refund）、WAV 魔数与实际字节时长校验、音频不落盘。
- 密钥：`.env` 已被 gitignore，扫描未发现硬编码密钥；`JWT_SECRET` 启动强校验。
- 测试：633 个用例全部通过（含记账幂等、预览确认、FAQ 检索、STT、权限矩阵、SQLi 登录等）。

## 四、优化方案（按优先级）

### 1. 流式历史去重（P1-1）——对齐非流式：先组包、后落库用户消息

```python
# routers/ai.py  event_gen 内调整顺序
history = await memory.build_history(gen_db, body.session_id)
system_prompt = await _build_system_prompt(gen_db, user_id, body.message)
messages = [SystemMessage(content=system_prompt), *history,
            HumanMessage(content=_safe_user_text(body.message))]
await ai_crud.add_message(gen_db, body.session_id, "user", body.message)
# 随后流式产出；"失败也保留用户消息"的语义不受影响
```

### 2. 历史脱敏（P1-2）——组包处统一清洗 user 消息

```python
from ai import security as ai_security
...
content = ai_security.sanitize(m.content) if m.role == "user" else m.content
picked.append(cls(content=content))
```

### 3. 前端处理非 200（P1-3）

```js
if (!res.ok) {
  let msg = '对话失败'
  try { const j = await res.json(); msg = j.error || msg } catch {}
  message.error(msg)
  setLoading(false)
  return
}
```

### 4. 并发槽泄漏（P1-4）——`_quota_gate` 纳入 try/finally

```python
release = await ai_concurrency.try_acquire(user_id, plan["concurrency"])
if release is None:
    return StreamingResponse(iter([sse({...CONCURRENCY_LIMIT...})]), media_type="text/event-stream")
try:
    quota_error = await _quota_gate(db, user_id, "chat", plan=plan)
    if quota_error:
        return JSONResponse(status_code=429, content=quota_error)
    return StreamingResponse(event_gen(), media_type="text/event-stream")
finally:
    release()  # 注意与 event_gen 内的 release 协调，避免双释放
```

### 5. Embedding 护栏（P2-5）

```python
_embeddings = OpenAIEmbeddings(model=EMBEDDING_MODEL, api_key=AGNES_API_KEY,
                               base_url=OPENAI_BASE_URL,
                               timeout=LLM_TIMEOUT_SECONDS, max_retries=0)
```

### 6. 中长线

- `_slots` / `_agg` 加惰性清理或容量上限；token 落库 `ai_usage_daily` 并加每日 token 上限。
- `risk_level` 用 `Literal` + 后校验；FAQ 向量落库、分批重建。
- prompt 集中到 `ai/prompts.py`，支持配置化与版本化。
- 多 worker 上线前，配额 / 并发 / 限流 / 观测统一迁 Redis / 落库。

## 五、待确认项

1. 部署形态：是否单 worker 单机？这是所有内存态护栏正确性的前提。
2. 数据合规：与 Agnes 是否有 DPA？当前脱敏是正则启发式，姓名、地址等仍会上云。
3. 实际使用版本：若线上实际运行的是基础版 `fast_backend`（AI 模块较旧），结论需平移核对。
4. 真实成本数据：是否有上游账单可验证 token 估算偏差（流式 / 结构化输出计量仍不精确）。
5. 前端修复范围：P1-3 需跨端确认（Web + uniapp 是否同样不检查状态码）。

## 六、总体结论

**主要风险**：历史消息 PII 绕过脱敏上云（P1-2，合规面最大）、流式上下文重复计费（P1-1）、并发槽潜在泄漏（P1-4）、前端配额失败静默（P1-3）。

**上线建议**：不建议直接多实例部署；单 worker 自部署可接受。4 个 P1 均为改动小、风险低的修复，建议修完后上线；P2 中 Embedding 超时与内存上限应在正式运营前处理。

**下一步行动**：先修 P1-1 / P1-2 / P1-4 + P2-5（后端，各配 1 条回归测试：流式消息不重复、历史含手机号时进 LLM 的为 `[PHONE]`、配额异常后并发槽可再获取）；再与前端一起处理 P1-3；长线做 token 落库与多 worker 迁移。
